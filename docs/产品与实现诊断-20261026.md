# 产品与实现诊断（2026-10-26）

## 结论与范围

当前工程更接近“接口闭环验证版 + 页面壳 + 持续补功能”，没有达到原型所表达的完整产品体验。问题不仅是美术不足，还包括真实能力被模拟效果替代、业务状态跳步、用户任务设计不足、文档与验收口径失真。

本次检查了根目录技术方案、设计方案、产品原型设计思路、交接文档，以及原型 README、两端关键源码、实际运行后台源码、后端支付与商户/结算路由、跨端测试脚本。结论来自静态审查；没有重新运行小程序、真实支付、真机扫码或数据库写操作。文档中的“全绿”不作为本次已验证结果。未修改业务代码；经用户允许初始化了 CodeGraph。

## 为什么原型体验更完整

原型 README 定义了对子页面、死链、返回、跨页数据一致性、任务状态机、溢出和真实点击的多项专项验收。实际工程的 automator-ui-e2e.mjs 主要验证 MOCK 支付、读取展示数字、手输核销、通过管理开发接口跳过观察期、评价。

这套测试有价值，但覆盖的是一种受控主路径；它没有证明真机扫码、真实资金流、陌生商户入驻、支付取消恢复、购物配送、任务作品选择等完整用户任务。该脚本部分失败结果只打印日志，而不立即抛错，也降低了“脚本结束=业务成功”的可信度。

原型的任务叙事、场景插画、信息层次没有被完整转成页面规格。正式首页以问候语、技术能力说明和线路列表为主；“真实交易”“后端同源”“HMAC”“完整商城 P2”等文案直接进入产品。游客需要知道去哪里、有什么体验、何时出发、费用包含什么、出现问题如何处理；工程完成说明不能替代这些内容。

不能照搬原型全部功能。原型的旧推广比例、角色拆分、链/NFT 展示等受后续定稿约束；应继承交互质量和任务完整度，按最新决策重新映射。

## 过程根因

1. **完成定义偏向接口和页面存在。** 页面可打开、状态能改动，就被汇总成能力已完成，缺乏用户独立完成任务的证据。
2. **缺少逐页规格与追踪矩阵。** 方案列模块、接口、表结构，实施需要的加载/空/错/权限/失败恢复状态没有形成统一验收清单。
3. **模拟能力与真实能力边界不清。** 有载荷不等于二维码可扫，有分账数字不等于实际分账，有输入框不等于可用编辑器。
4. **广度扩张快于核心打磨。** 当前后台新增 WEB3、暗号、共创、资产等入口，而核销、支付、结算与商户准入还有基础缺口。
5. **设计基准与代码现实脱节。** 总方案写 Spring Boot、Next.js/Ant Design Pro，README 明确实际主入口是 Node API 与手写 SPA。换栈本身不是错误，但必须同步组件规范、验证方式与唯一维护入口。
6. **交接记录失效。** 10-25 文档仍列约稿、离线核销、自助入驻等“未做”，当前源码已有相应追加实现。不能凭旧文档宣称缺失，也不能凭新入口宣称成熟。

## 建议执行顺序

### 第一批：修复真实性与权限

真实二维码编码和真机扫码；取消凭门店 ID 自动入职；修复支付配置读取并做真实沙箱/小额验证；结算改为合法状态转换并关联真实通道结果；演示模式显式隔离；失败显示错误与重试，不显示虚构余额。

验收必须留下：测试身份、初始状态、操作、页面反馈、服务端结果、失败恢复、截图/日志。真实分账未接通时明确展示“待人工支付”等真实状态。

### 第二批：按完整任务重建三端体验

- 游客：目的地/主题发现 → 详情 → 团期与费用确认 → 联系人与出行资料 → 支付 → 凭证/通知 → 评价/退款。商城另行明确是到店兑换、预约商品还是配送实物。
- 商户：申请/审核进度 → 安全加入门店 → 按角色工作台 → 核销及异常处理 → 库存/订单 → 对账异议 → 确认与到账。
- 后台：待办优先，围绕进件审核、商品发布、退款处理、结算复核、内容审核组织工作。使用可校验表单、详情与历史记录，减少 prompt 对话框。

### 第三批：建立新的完成门槛

建立“最新决策 → 页面 → API → 表/状态机 → 验收证据”矩阵；每项标记未开始、接口可用、页面可用、模拟联调通过、真实业务验收通过。选定一个生产实现分支，将另一个标为参考/归档。更新交接文档，停止使用笼统的“全部完成”。

不建议先整体换栈或继续堆新模块。先把一条真实游客交易和一家真实门店经营流程做完整，再扩展推广、创作与生态功能。
