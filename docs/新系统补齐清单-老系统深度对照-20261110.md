## 1. 结论与证据边界

老系统最值得吸收的是三层经营结构：**可复用的商品/服务 → 多提供方主题游组合 → 每位销售人员的产品授权及佣金**。这三层在旧后台有实际记录，在两个 H5 上也能看到部分对应结果。现有系统的内容字段并不全面落后，但交易主线主要围绕单一履约商户；推广工作台也比老销售端简略。

因此，补齐工作应同时处理业务模型、端上操作和内容维护，不能把所有差距变成表单加字段，也不应复制旧系统的财务规则。

### 1.1 已确定的三端职责

三端入口能够承载目标业务；下面的新增能力仍须开发和验收，不能把架构可承载表述为现有功能已齐备。

|---|---|---|
| 游客购买与出游 | 游客小程序 `mini-a` | 套餐内容、服务项权益/使用进度、预约与售后、可信行程及产品勋章；独立自由豆补贴券账户及下单抵扣 |

## 5. 逐项开发要求与验收标准

### D01 商品促销折扣（负责人新增）

第三批优先交付通用商品折扣，不把已有早鸟价/自由豆满减当作已完成。原价299元打8折为239.20元；原价来自真实团期价格，界面填写8折，服务端统一计算、建单留快照。早鸟与商品折扣择低不连乘；默认不叠加自由豆/旅豆，可明确配置允许，允许自由豆时按折后金额判断门槛（239.20再减50为189.20，无保费示例），自由豆与旅豆仍互斥。折扣不自动生成官方补贴责任，退款/佣金/结算/毛利按真实实付与快照核对。GLM实施，Codex独立验收；字段、精度、UI与边界详见[D01实施与验收](商品促销折扣-D01实施与验收-20261110.md)。

### B01 独立商品/服务供给项台账

**差距依据：**旧 O01 为供给单项建立成本/售价；我们已有 supplier、merchant、scenic 和景区票种，但线路 product 仍主要对应游客购买对象，尚未看到可供多线路复用、贯通核销结算的通用供给项台账。商城 `cat=shop` 也不能直接等同于供给项。

建议字段：

| 分组 | 字段 | 说明 |
|---|---|---|
| 标识 | 编号、名称、商品/服务类型、类目、状态 | 区分资源下架与历史订单履约 |
| 主体 | 提供主体、履约门店、所在城市、业务联系人 | 复用现有主体/门店，避免自由文本造成重复主体 |
| 商品资料 | 封面、图集、详情、单位、规格、服务时长、适用人数 | 例如“一间夜”“一人次”，不能仅写一个名称 |
| 经营 | 成本单价、参考零售价、币种、计价单位、有效期、协议版本 | 成本按分存；参考售价不直接覆盖套餐销售价 |
| 履约 | 预约要求、开放时间、可用次数、容量/库存规则、不可用日期 | 第一期可只支持明确的少量库存模式 |

验收：一个“咖啡一杯”可加入两条主题游；停用后不能加入新组合，但已售快照保留；成本调整不改历史订单；未授权游客/销售接口不下发采购成本及收款资料。

### B02 主题游套餐组合与订单快照

**差距依据：**O02 已存在多提供方组合。当前 product 表单只有一个履约商户、一个供应商、一个景区；`domain/order.mjs` 下单写入单一 `merchant_id`，没有看到对应通用套餐项快照流程。

要补：

- 产品组合明细：供给项、数量、单位、提供者、履约门店、必用/可选/赠送、预约要求、可用期限、顺序、适用团期。
- 组合项配置版本；发布后更改组合生成新版本。
- 订单创建时保存名称、数量、履约主体、价格分摊、成本/规则版本的快照；只保存资源 ID 不够。
- 订单详情增加套餐内容及每项履约状态，游客和商户各取授权字段。
- 既有单商户线路按原逻辑继续工作，迁移不重写历史订单。

验收：套餐“民宿＋咖啡＋果盘”由 A/B 两店提供，下单后改产品配置不影响旧单；游客能看权益清单；A 店只能看并操作本店项，B 店同理；不能因套餐里有多项而重复扣款、重复赠豆。

### B03 按项核销与部分履约

**差距依据：**O08 有单项状态。当前 `domain/pass.mjs` 的 `issueForOrder` 按购买人数 `qty` 发通行凭证；核销按订单单一商户校验，全部有效凭证核销后推主订单状态。**按人多张票与按服务多项核销是两种能力。**

要补：服务项/参与人维度的权益实例、对应核销主体、应核销数量、剩余次数、有效时段、核销人、核销时间、撤销/异常处理记录。游客出示码后，商户只能选择自己有权履约的项；历史防重放、日期窗、离线冲突不能丢。

主单展示“未使用/部分使用/全部完成”，并单独定义哪些赠送项不影响完成。不要直接把当前主状态 40 当成“任意一项已核销”。

三端承接：游客小程序订单详情展示各项、使用方式、预约要求、剩余次数及售后入口；商户小程序工作台/订单中增加本门店服务任务，支持按日期、预约及待履约状态查询，扫码后展示可办理项并确认；PC 订单详情展示全项进度、异常与售后处置。店员按岗位只核销，老板/店长才按权限管理接待与查看金额；PC 留存操作轨迹。履约人员必须绑定合法门店/服务组织，不能借“共创”身份直接放行核销。

验收：咖啡核销不会核销住宿；重复扫咖啡不会重复记收入；跨门店不能越权；两店并发核销结果一致；部分完成后不能提前触发全部返豆/勋章；未履约项取消后如何结束订单须有明确规则。

### B04 多提供方成本、分账、部分退款

**现有能力：**`domain/promo.mjs` 的 generateSettlement 按 `orders.merchant_id` 汇总已完成订单，按履约、服务、权益、推广、留存五口径计算；共创分润从留存金额切出。它不是旧 O02 的“每个组合项按成本支付给各提供方”。

先确认三个问题：套餐实收如何分摊到各项；供给成本从哪一口径支付；部分使用/赠送项/退款时各方应得如何变化。**不得在五口径之外再无条件追加成本支付，造成重复支付。**

要补的数据：订单项分摊金额、成本快照、履约应付、分润基数及版本、退款分摊、调整分录、结算关联、付款登记。合同承诺成本与会计应付、实际付款应分开。

规则建议供评审：未使用项按经确认的分摊规则退款；使用项保留履约事实；优惠、旅豆、手续费和保费分别处理；以最小货币单位分配尾差；历史规则只冲正，不覆盖。

验收：同一份实收可复算到各项及各口径；退款后返豆、佣金、成本应付、分润一致；已结算/已打款再退款走调整而非直接删除；重复回调及重复结算不会重复支付。资金商投资额的登记不自动代表应付本金或保本承诺。

### B05 销售授权与人员×产品费率

**差距依据：**O04 同一产品不同销售费率。现有 `promo.createCommission` 读取产品覆盖费率与推广员档位，不含人员×产品关联费率；现有产品覆盖有生效期及 12% 封顶，应保留。

要补：推广员 ID、产品 ID、可售状态、授权开始/结束、可选约定费率、生效期、协议/审批号、变更原因、操作记录。授权控制必须在后端取码及计佣校验中执行。

建议优先级供评审：有效人员×产品约定 → 有效产品统一覆盖 → 推广员档位；仍受现有上限约束。计佣保存命中规则、基数、费率、金额和授权版本。

现有系统采用首触归因。产品码引入后必须先定：是继续用户首触，还是特定活动有经确认的产品归因规则。二维码带销售人员并不自动授权改写归属；不得悄悄改掉已有首触规则。

验收：同一产品给 A/B 不同约定费率，分别正确计算；未授权不能取专属产品码；到期/撤销后新单行为符合确定规则；老单可复算；自购不计佣、退款冲正及冻结暂停继续有效。

### B06 产品专属推广码与素材包

**差距依据：**当前 `/c/promote/qrcode` 固定生成到 `pages/home/index` 的推广码；分享也到首页。O05/O06 是按具体产品取码。

要补：推广员+产品+活动/渠道的服务端记录；在游客小程序推广中心生成对应产品的小程序码、微信分享卡片、海报及转发文案，目标定位游客小程序产品详情。若首触规则保持不变，应明确“推广来源”和“最终计佣归属”的区别。普通链接/普通二维码仅在现有微信能力可支持且有实际传播场景时补充，不为它新增 H5 落地页。

验收：微信扫码、好友分享卡片均能到正确产品并记录来源；冷启动/已登录场景都能保留有效来源参数；产品下架/授权过期显示有效提示；无效参数不能冒充他人；未配微信凭据显示待配置，不把 mock 图片称为真码；海报价格更新及失效策略明确；相册保存权限被拒后可恢复操作。

### B07 游客小程序推广中心升级为销售工作台

落在现有 `mini-a/package-promo` 分包，以「我的 → 推广中心」为主入口，按需要新增产品列表/推广素材、佣金明细、提现申请/记录/详情页。复用原微信登录、B05/B06/B08 和现有计佣逻辑；保留现有推荐客户和原推广码兼容能力。

| 页面 | 最少信息与动作 |
|---|---|
| 可售产品 | 产品、封面、卖点、销售价/起价说明、可售团期及剩余名额、有效费率、授权期、生成码 |
| 业绩 | 时间/产品筛选，成交额、有效订单、观察期佣金、可提佣金、冲正金额；逐笔基数及费率 |
| 提现 | 当前可申请额、待处理占用、收款账户尾号、规则、申请记录、状态时间线、退回原因、付款凭证 |
| 身份与账户 | 当前推广身份、授权状态、收款账户尾号及维护指引；冻结/资格失效反馈，与小程序「我的」共用 |

资格由 PC 后台开通、授权产品和设置费率；推广员进入小程序后由服务端返回能力及数据范围。未开通显示申请/联系运营说明，资格停用后保留授权允许的历史查询并暂停取码和资金动作。手机号绑定按现有正式登录/核验流程处理，不增加独立销售账号密码或浏览器短信登录作为本轮依赖。

验收：真实游客小程序可完成微信登录、查看授权产品、生成/分享产品码、查询佣金、申请及追踪提现；只见本人业务；返回路径与分包跳转正常，拒绝相册授权后可重试；网络错误显示明确状态；停售、资格失效、冻结和重复申请的后端守卫有效；普通游客的浏览购买流程保持可用。新页面登记到 `api/admin/miniapp.js` 的 MINI_MAP，并补对应页面与接口的验收证据。

### B08 提现与打款的透明流程

**明确差距：**游客推广中心目前只有汇总、待审笔数、全额提现；本次核对的游客接口未见本人完整佣金/提现分页查询。`admin-ops.mjs` 的推广提现 verdict 将“通过并填写真实流水”直接登记为已支付，状态为待审/已付/驳回；尚未分开“审批通过、等待打款”。共创分润后台已有独立付款/回单能力，不要重建。

要补：

- 本人佣金和提现明细查询，支持分页、时间与状态筛选；分开成交额、计提、放行、申请、实际打款。
- 提现单状态建议为待审核、已驳回、待打款、已登记打款；实际银行到账只能在有确认依据时声称。
- 申请金额与待处理占用；默认可先保留全额申请，是否支持部分申请单独定规则。
- 审核意见（驳回必填）、收款账户快照、打款人/时间、流水、附件、失败/撤销/重提记录。
- 本人授权下载回单；不能公开挂出银行与证件文件。现有共创附件受控下载可复用思想和基础能力。
- 拆分状态后同步修正余额、待审锁定、日限额、并发守卫，不能只加一个前端标签。

入口归属：推广佣金申请/记录/回单进入游客小程序推广中心；共创分润与付款进入游客小程序合作中心（B13）；门店经营结算继续在商户小程序。三类余额、单号和审批口径分别展示，不能因为同一用户兼任角色就混成一个可提现总额。审核、真实付款登记、回单上传仍由 PC 财务办理。

验收：审批通过还未付款不会显示已到账；待打款占用防重复申请；退款冲正导致可提不足有明确处置；冻结后资金动作停止；本人可看到驳回原因与真实付款证据；他人无法查询或下载。

### B09 视频、服务权益与实际移动预览

**差距依据：**当前 product schema 图集为图片，富文本工具提供图片；游客详情首屏也是 image 轮播。未见产品专用视频字段、播放链路和完整手机预览。现有亮点、标签、费用包含已经有，不再重复新增。

建议新增：视频文件/URL、封面、时长及顺序；结构化额外服务（名称、是否包含、数量、限制、是否另收费）。旧字段“增幅服务”不要原名照搬；收费加购涉及价格与退款，应另立规则，不能藏在文案里自动收费。

PC 后台提供使用游客真实公开字段的手机尺寸预览，并安排游客小程序实际页面验证；需真机预览草稿时，使用短期受控预览凭证和指定审核身份。草稿不能出现在公开销售列表，也不能依靠猜测产品 ID 访问。编辑器、接口白名单、游客小程序渲染三处一起接入。

验收：视频上传/校验、封面、播放、弱网反馈正常；费用包含与额外服务不冲突；手机预览和小程序已发布展示一致；采购成本、银行信息及内部暗号不因预览泄露。

### B10 报名截止从展示变为业务约束

**确切证据：**session schema 的 `sign_deadline` 帮助文字明确“展示用，到点请将状态改为已截止”；`domain/order.mjs` 的 place 主要检查团期状态、名额、产品及商户状态，未读取该截止字段。旧系统有截止字段，但本次也未验证旧后端是否真正拦截，不能把它当作已验证实现。

要补：统一业务时区的截止时间；列表/详情的可售状态；下单服务端判断；截止后旧未支付订单的支付策略；容量锁定/释放仍走现有事务。状态没来得及被定时任务修改时，仍须拦截新下单。

验收：截止前可下、截止后一秒直调接口也被拒；跨零点正确；已支付单继续履约；未支付单按确定的付款规则处理；修改截止时间有审计。

### B11 三端内频道、活动与产品可见范围

现有产品有 `channel` 字段及主题频道 `cat`；当前产品编辑器和游客列表还不能据此视为已具备完整定向发布能力。本轮采用一个游客小程序、一个商户小程序，不复制旧系统按人群拆不同前端；“姐姐行、亲子、体育”等优先用游客小程序内频道、专题或活动承接。

PC 配置频道/活动、公开销售或定向可见范围、封面/标题/顺序、生效期；游客小程序按规则展示，推广中心另按 B05 显示可推广范围。商户小程序按履约项与门店授权查询，不能拿游客可见范围当商户履约权限。公开可购买与某推广员是否有权计佣也必须分开。

验收：普通游客、定向活动用户、授权推广员、门店员工看到符合各自规则的内容；列表与详情直链一致；套餐主库存同源，门店服务容量按 B01–B04 规则处理；频道或活动停售不阻断历史履约。多品牌/新增 AppID、H5 发布均不列入本轮开发或验收范围。

### B12 产品经营总览与办理流程

**2026-11-10负责人补充：成本价、实际销售价、产品/订单毛利与毛利率、平台经营收益须能直接展示和下钻。** 该部分与B01/B04在第三批交付，不等到第四批。当前前两批经营总览仍不等于已具备完整成本利润看板。

必补：供给项成本/参考售价及单位/有效期/版本；产品套餐成本合计和实际销售价、预计毛利/毛利率；订单成本/售价/优惠快照、确认成本/退款调整及已确认毛利；按期间/产品/城市汇总和下钻。预计与实际确认分开、缺失成本不当0、负毛利提示、零收入不算百分比，汇总毛利率用合计毛利除以合计同口径净销售额。

商品毛利与平台经营收益分开；GMV和五口径留存不等于净利润，成本/分账/佣金/补贴不能重复扣算。例：售价199、成本120，毛利79/39.70%；自由豆后现金149、成本120，现金商品毛利29/19.46%，官方补贴50另列。完整口径、权限和验收算例见[GLM后续交接](GLM后续实施交接-Codex独立验收-20261110.md)。

当前资料、供应商、共创分润、逐品佣金、资金分布在不同页面；建议增加产品经营总览，而不是继续新增孤立表单。

至少聚合：销售资料/完整度、发布范围、团期/名额、供给项与门店、成本及有效协议、销售授权及有效佣金、奖励规则、履约进度、结算/退款/付款入口；按权限展示敏感信息。

维护路径建议：基本资料 → 服务组合 → 履约与资金规则 → 销售授权 → 预览及发布预检。第一版可先把已有页面做产品级聚合，新增组合能力后再接入。

验收：运营能从一款产品查清“卖什么、谁履约、如何结算、谁能卖、还缺什么”，各数字能进入真实明细；只读角色不能通过入口越权修改；没有接口的卡片明确未开通，不填装饰性数字。

### B13 游客小程序合作中心与共创项目查询

O08 同一主体兼三角色。当前 merchant/supplier/co_creator 各有合理边界，co_creator 表单为资金商/商品商单选且绑定一条线路；不能简单改成一个多选字段就认为完成多角色身份。

主体与经办人绑定先按 B16 完成，再在 `mini-a` 增加「我的 → 合作中心」及对应分包页面；PC 后台负责开通、授权项目及维护合作关系。证照和收款资料复用原主体档案并留变更记录，不让合作方重复提交一整套门店进件资料。

| 合作中心页面 | 最少内容 |
|---|---|
| 主体/项目列表 | 当前经办主体、共创角色、授权项目、合作状态及协议有效期；多主体明确切换 |
| 项目详情 | 关联产品、投入登记、分润规则及版本、生效期、规则基数说明；登记不等于已回款或本金保障 |
| 分润明细 | 期间、结算依据、基数、比例、应计、调整、已付款/待付款；分页和日期/项目筛选 |
| 付款与凭证 | 每笔付款金额、时间、状态、流水及受控回单，冲正/撤销明确展示 |
| 账户与异议 | 收款账户尾号、变更申请/运营维护指引；对账疑问可关联已有工单或受控反馈流程并追踪处理结果 |

共创项目查询与推广提现分开；本轮默认复用现有 PC 共创分润审批/付款登记，不凭空新增“共创可随时全额提现”承诺。是否允许共创自助提现须另定业务规则。服务履约任务放在商户小程序，合作中心可按权限提供汇总/跳转指引，但不执行门店核销。本轮不建设共创 H5。

验收：纯资金合作方无需成为门店员工即可在游客小程序查询本人授权项目；一主体多个项目/角色不重复建银行资料；切换主体后明细/回单均换到正确范围；纯资金角色无核销权限；历史记录可分页查询；未绑定用户的共创档案不能凭手机号直接查询资金信息。新增页面登记 MINI_MAP，并验证真机返回、文件查看与失效权限。

### B14 产品专属勋章与奖励配置

O11 主题游可选勋章，O12 手册描述服务完成后发勋章。当前已实现 order_count、城市、评价、成长等自动规则，但本次核对的 `badge.mjs` 自动规则未含“完成指定产品/活动”，product 表单也没有直接配置专属勋章。

建议扩展现有规则：适用产品/活动、完成条件、勋章 ID、规则版本、生效期、发放上限、重复获得策略；沿用现有 grant 幂等、发行上限、可信记录。返豆已有 bean_gift，不重做积分发行，也不复制旧合约地址输入流程。

验收：完成指定产品获得对应勋章；部分核销不误发；重复回调不重复发；上限与过期规则可解释；退款后保留旅行事实还是撤销权益先定口径并留记录；界面沿用现有旅豆/勋章用语。

### B15 字段口径、内容与表格可用性

本项可以先做，不等新模型。

1. **共创分润口径统一。**entity-schema 的共创 share_pct 帮助写“按线路结算金额计提”，但实际 `promo.generateSettlement` 从留存金额按产品 GMV 占比分配后切分。应先统一表单、列表、说明和核对公式，避免把交易额误当分润基数。
2. **推广中心规则读取服务端。**当前 WXML 写死满 ¥100 申请和 T+7；后端使用参数 `promoter.withdraw_min`、`commission.settle_delay_days`。接口需下发真实规则，按钮和说明同步；不要照搬旧 H5 的“最低 ¥10、2 小时到账”。
3. **推广页字段契约。**当前模板读取 `overview.validGmvLabel`，页面 data 主要使用 ov，overview 汇总接口也未返回此字段；客户列表模板读取 statusText，接口返回数值 status。应补正确数据映射与明确状态文案，而不是让默认兜底掩盖缺项。
4. **线路内容一致性。**现有实际列表有“标题 2天1夜、行程天数一日8小时”的条目，以及商城实物带旅游时长的样例；应逐条核对天数、适用单位、成团/预约方式、费用、图文、城市与供给关联。不把高完整度当内容正确证明。
5. **完整度按产品类型解释。**当前完整度按非空字段比例计算；实物商品、到店体验、线路不应要求完全相同字段。已有上架守卫应继续使用，再补分类型必需项与发布预检。
6. **表格增强按实际任务做。**现有商品列表已经显示供给链，旧系统也并非所有表都更丰富。优先加可售状态/下个团期/剩余名额、服务项数量、授权销售数、最近资料维护时间及明细入口；人员表补角色关联与协议有效性。支持查询/分页/导出时，复用已有角色及城市隔离，不默认全量开放银行卡、证件列。

验收：前后台金额和规则文案一致；调整参数后端上同步；一个产品标题、天数、行程、团期和购买单位互相一致；列表数字可解释并能进入对应明细；资料未适用字段不会诱导填假内容。

### B16 三端多身份、主体/门店授权与入口联动

这是本轮明确增加的共用能力，确保两个小程序能承载游客、销售、共创和商户多角色。下述为实施要求，不代表现有跨端绑定或合作身份已实现。

| 层次 | 必须表达的关系 |
|---|---|
| 登录用户 | 用户主 ID、微信 AppID/openid 关联、正式核验状态、停用状态；不向前端公开身份关联凭据 |
| 业务主体 | 自然人/机构主体与商户、供应商、共创档案的关联；主体可有多个经办用户 |
| 授权 | 用户×角色×主体/门店/项目×有效期×状态×操作能力；必要时明确城市范围 |
| 当前工作上下文 | 游客小程序当前推广/合作入口及合作主体，商户小程序当前门店及岗位；切换后重新取数 |

**PC 后台：**增加主体关系和经办人授权入口，支持查找现有用户、绑定/解除、岗位及项目范围、期限、停用和审计；避免把同名或同手机号档案自动合并。收款账户变更需按现有资金权限审核，授权经办人不自动取得财务审批权。

**游客小程序：**「我的」由服务端返回可用工作入口；一个用户可同时是游客、推广员和多个合作主体的经办人。普通游客无需选择工作身份才能下单；工作入口在页头明确当前角色/主体。切换后清空旧主体缓存及分页数据，返回与重新进入都保持正确范围。

**商户小程序：**复用老板/店长/核销员体系，补多门店选择与明确当前门店；订单任务、核销、库存/预约、结算查询及修改操作分别按岗位授权。仅有共创分润资格不能进入门店工作台。

**后端：**每次读写校验用户、有效授权及目标资源归属，客户端传主体 ID/门店 ID 仅作请求上下文，不能直接当授权。跨 AppID 不凭客户端提供的 openid 或手机号合并；可用经服务端验证的统一身份关联，无法自动确认时走受控绑定。角色/资格停用后的会话和缓存应失效或在下一次请求重新校验。

**接口边界：**推广明细、合作项目与回单、门店任务分别返回最小字段；合作查询可新增明确的本人接口域，不能直接放行现有 `/admin` 查询接口。复用计算逻辑与数据源，读取范围仍须独立校验。

验收：同一用户可在游客购买、推广工作、合作项目间切换；跨主体替换参数被拒；有两门店授权的员工能切换而不串单；核销员看不到不该看的资金，资金合作方不能核销；PC 撤权后旧会话不能继续敏感操作；两个 AppID 的绑定、解绑、换微信账号与未绑定状态有明确反馈；游客正常购买不受工作资格停用的无关影响，账号整体冻结仍按现有规则执行。

### B17 自由豆：官方补贴专用券式积分体系

#### B17.1 产品定位与首版默认规则

负责人要求增加「自由豆」，用于官方直接发放优惠补贴，例如商品 199 元，后台配置满 100 元减 50 元，用户符合条件后实付 149 元；与原旅豆体系并存。

**首版设计为券式积分权益账户：**每份自由豆权益绑定发放批次、使用门槛、减免额、适用范围和有效期，后台发给指定用户/人群，用户在符合条件的订单上使用。先支持「满 X 减 Y」固定减免，不把所有权益变成无条件通兑的余额。

这里的「自由豆」是官方补贴权益名称，不直接沿用旅豆兑换比例。界面展示“自由豆 · 满100减50”“可用补贴券2份”等清晰内容，可汇总券面补贴额度，但不同门槛/范围的额度不能合并抵现；首版不自行设定“1自由豆=1元”或“10自由豆=1元”的通用兑换率。若后续需要统一豆数余额和兑换比率，再作为明确的业务扩展，而非让 GLM 自行猜一个比例。

本轮默认：官方定向/批量发放；不可购买充值、转让、提现或兑换旅豆；不由消费自动产生自由豆。每单最多使用一份权益，固定满减、不拆分、不找零；门槛基数为采用实际售价/早鸟价后的商品合计，不含保费及其他代收款，不按划线原价凑门槛。要求 `0 < 减免额 < 门槛额`，且优惠后应付保持符合当前支付通道的最小金额要求。

**与旅豆同系统并存，首版同一订单互斥使用。**结算页允许选择旅豆抵扣或一份自由豆补贴，显示选择前后明细，不静默扣用户另一种权益；不修改现有旅豆单的抵扣比例、预算、发放、返还和账本。跨订单可以分别使用。自由豆与旅豆叠加暂不开放，后续必须明确顺序、门槛、上限、奖励基数和补贴来源后才能启用，不能只加前端开关。

以上为可实施的首版默认方案；用户明确的补贴例子和独立体系是确定范围。GLM 应先按此方案实现并留测试，不因“自由豆是否等于多少元”自行暂停，也不得暗自扩展为可充值、交易或提现的积分。

#### B17.4 计价、资金来源与旅豆经济边界

无旅豆、无保费的示例：

| 项目 | 金额/结果 |
|---|---|
| 当前商品成交价 | ¥199.00 |
| 自由豆规则 | 满 ¥100.00 减 ¥50.00 |
| 是否达标 | 199 ≥ 100，可用 |
| 自由豆官方补贴 | ¥50.00 |
| 旅豆扣减 | 0 |
| 微信实际支付 | ¥149.00 |

商品 99 元不达标；199 元没有这份权益不能自动享受；前端改价或篡改权益ID一律由服务端重算并拒绝。试算和最终建单应使用同一规则入口，建单时复核适用范围、余额/权益状态、预算及库存；金额或资格变动需用户重新确认，不能暗改实付。

**独立记账不等于补贴没有成本。**50 元必须有独立官方营销预算和资金来源；优惠不能通过增加旅豆发行、挪用旅豆预算、制造现金收入或重复计入留存来补平。

首版保护原则：旅豆既有单及历史五口径分账规则不变；自由豆单的 `amount_pay` 仍如实记录微信实付 149 元，不能伪装成199元。现有按现金实付计算的佣金等继续读取真实现金口径，不把官方补贴重复当成新销售额、佣金基数或消费返豆来源。赠豆/成长奖励原有计算入口必须逐一核对，确保不因“补贴额”字段意外放大发行；若原规则本身按固定产品赠豆，则仍按原规则而非擅自改为按149元赠豆。

官方承担的50元另建补贴应付与付款/冲正流水，按活动确认的承担方和履约受益方结算，不混成原五口径的第六份无来源收入。单商户场景可将其列为该商户的独立补贴应收；多商户套餐必须沿用 B04 经确认的订单项分摊，合计不超过50元。原实付分账与新增官方补贴补偿应分别对账，禁止把199元先完整分账再额外支付50元。

因此“满100减50”在首版不承诺所有参与方的收入都与未优惠的199元订单完全相同：现金实付变化会影响原按实付计算的结果。若业务要求商户/推广员各方按优惠前金额保额，必须另列官方补偿规则及预算来源后实施，GLM 不得自行放大佣金或修改五口径。未启用自由豆的订单必须与旧实现结果一致。

#### B17.5 权益状态、并发与退款

1. 发放：审批预算及批次 → 预占最大补贴责任 → 幂等授予用户权益。
2. 试算：只读资格与金额，不扣权益；用户选择后显示清晰的现金应付。
3. 建单：同一事务/可靠一致性流程中锁定权益、验证预算与名额、建立订单快照；任一步失败须回滚/补偿，不留扣豆无订单。
4. 支付成功：以回调金额与订单实付匹配为准，权益从锁定转已用，补贴承诺转已用责任；重复回调不得重复核销或重复计补贴。
5. 取消/超时：未支付单释放权益锁定与相应订单占用；仍在有效期可重新使用，已过期则归还预算未用责任并明确失效；迟到支付沿用现有退款处理并核对权益/补贴状态。
6. 全额退款成功：只退实际收取的现金（例149元，不退199元），补贴应付撤销/冲正；符合返还条件的原权益仅返一次。权益仍在有效期则恢复可用；已过期则记为过期，不私自延长或另赠一份。退款失败或处理中不提前释放已用权益。
7. 部分退款：使用 B04 订单项快照分摊，现金累计退款不超过实付、补贴累计冲正不超过已使用补贴；首版部分退款不恢复整份券，剩余责任与已用状态保留可核对。不得用退款制造新自由豆；套餐部分退款规则未闭环前不得上线该组合。
8. 已付补贴后退款：走有来源的应付调整/追偿/下期抵扣记录，不删除历史付款。账户冻结、活动停发及批次撤销各自作用范围明确，不能破坏已售履约。

#### B17.6 专项验收

- 满100减50：99元不可用，100元实付50元，199元实付149元；按真实售价计算且不含保费。
- 无自由豆资格、过期、已使用、范围不符、活动受限、预算不足均准确提示；改参数/换用户ID不能越权抵扣。
- 同一权益并发下两单仅一单能锁定；重复发放、支付、取消、退款均幂等，失败无残留占用。
- 同单旅豆/自由豆互斥，取消选择可恢复另一种抵扣方案；旅豆余额、预算、发行统计和历史封存无自由豆混入。
- 原价/优惠/实付与微信支付回调一致；现金退款及补贴冲正分别守住上限；多商户分摊合计正确。
- PC、游客小程序、商户小程序及导出报表能核对发放、占用、使用、退款和付款，不以mock支付/凭证代替真实资金来源。
- 不启用自由豆时，原下单、旅豆抵扣、返豆、佣金、退款、五口径结算全量回归通过。

## 6. GLM 连续实施批次（不是暂停点）

### 6.1 执行约定

## 8. 验收场景与交付证据

后续实现至少准备这些场景，全部使用隔离数据；真实外部依赖单独验收。

| 场景 | 验收要点 |
|---|---|
| 两商户三服务套餐 | A 住宿、B 咖啡、A 赠送果盘；分别履约且不互相越权 |
| 两名销售推广同一产品 | 各自授权/费率及生效期正确，最终归因遵循确认规则 |
| 部分履约后退款 | 未用服务、已用服务、佣金、旅豆、分润/应付调整可对账 |
| 产品/协议/价格修改 | 老订单快照不变，新订单用新版本 |
| 销售授权撤销/冻结 | 新取码与资金动作被正确限制，历史明细仍按权限可查 |
| 提现审核与打款分离 | 未付款不显示已到账，待处理资金防重复申请，回单本人可查 |
| 报名截止边界 | 截止后一秒、跨日、直接调下单接口均符合规则 |
| 旧单商户回归 | 下单支付、核销、退款、结算、返豆/勋章、旧推广码继续正常 |
| 多渠道与敏感字段 | 不越端、不越主体、不泄露成本和账户，导出范围一致 |
| 游客小程序多身份 | 同一用户购买、推广、合作查询可切换；普通游客无工作资格也可正常购买；切主体无缓存串数据 |
| 合作中心 | 无门店身份的合作方能查授权项目和回单，不能核销；对账反馈可追踪，未承诺的提现不出现 |
| 商户岗位与多门店 | 老板/店长/核销员权限正确；切店后任务/预约/库存/结算各自隔离，跨店核销被拒 |
| PC 开通/撤权联动 | 绑定用户、授权产品/项目/门店、停用后，两个小程序及旧会话读取和操作范围同步生效 |

| 官方补贴资金核对 | 实付、减免、补贴预算/应付/付款分别可对账；没有把50元虚增为现金或重复分润，多商户合计正确 |

## 9. 不建议照搬的旧设计

- 有销售就不能停售：应允许停止新售并保留历史履约，不能把二者绑死。
- 页面“上链次数”、合约地址或台账“已打款”直接代表真实接入/银行到账：本次没有验证这些外部事实。
- 人员表默认全量展示证件及银行卡、表格保留明文初始/更新密码：不沿用。
- 资料模板将长证件号按数值保存：新导入必须按文本校验，避免精度损失。
- 旧页面的静态收益、到账承诺、首屏默认资料：本次观察到页面加载前会出现默认内容，应以加载稳定后的本人数据为准，新端使用明确加载态。
- 为每类角色复制用户、库存、订单、计佣、余额：两个小程序与 PC 全部复用同一业务系统，按角色和主体分入口与授权。
- 为追求字段数量强制无关资料：仅在对应主体/交易场景采集必要字段。
