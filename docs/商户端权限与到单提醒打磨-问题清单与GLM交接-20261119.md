## 一、先说现状（避免做重复功）

| 事项 | 现状（已读码） |
|---|---|
| 改价权限 | 服务端 `POST /m/supply/:sid`、`POST /m/supply/batch` 门槛是 `role >= 2`，**店长(2)和老板(3)现在都能改**；核销员(1)被拒。小程序库存页入口也是 `role >= 2`。**权限本身不缺，缺的是下面 M-01 的三个窝**。 |
| 到单提醒 | 「我的」页「到单提醒」只是一行点一下才调 `requestSubscribeMessage`；**没有开关、不知道是否已订阅、不会默认开**；服务端 `notifyMerchant` 把新订单/退款/结算**发给全部在职员工（含核销员）**，且不记谁订阅过。订阅模板正式 ID 属外部条件（X-05），只能在 MOCK 下验。 |

## 二、任务清单（11 项）

### P0

**M-01 改价权限：老板与店长一致可用，且权限变化即时生效**
1. **角色写死在 token 里**：登录时把 `role` 签进 7 天有效的 token（`merchant.mjs` 登录处 `jwtSign({..., role: staff.role}, 7*24*3600)`）。老板把店长降成核销员、停用员工、或把核销员升成店长，**旧 token 仍按旧角色行事最多 7 天**——降权后还能改价，升权后还点不了。改为：`requireUser`（商户端各接口入口）按 `merchant_staff` 当前 `role/status` 校验（短缓存不超过 30 秒），停用即 1002/1003，角色以库为准。
2. **断言补全**：`role` 1 拒绝、2 通过、3 通过，覆盖「单个改价、批量改价、早鸟设置、调名额、停售/恢复」五个入口；以及「改完角色后同一 token 立即按新角色」的用例。
3. **改价交互小细节**：输入限制最多两位小数、给上限提示；新旧价差超过 ±30% 弹二次确认（显示「¥旧 → ¥新（涨/降 xx%）」）；成功提示带旧→新价；冲突(2002)文案保持明确。
4. 验收证据：模拟器三套截图（核销员只读文案、店长改价、老板改价），见 M-11。

**M-02 到单提醒默认开启（核心）**
微信一次性订阅消息**无法静默开启**，必须用户手势授权一次，且一次授权只够发一条。所以「默认开启」按三层做，缺一不可：
1. **员工级偏好，默认开**：新增迁移（下一个编号，只增不改）给 `merchant_staff` 加提醒偏好（新订单、退款申请、结算待确认三项，默认 1）；`GET/POST /m/notify/prefs`；`notifyMerchant` 发送前按偏好过滤。**默认收件人：老板、店长；核销员默认关（可自行打开）**。现有员工回填：老板、店长三项为 1，核销员为 0。
2. **「我的」页改成开关 + 状态**：到单提醒一行显示「已开启 / 授权额度不足，点此补订阅 / 微信通知总开关已关，去设置」，用 `wx.getSetting({ withSubscriptions: true })` 判断；开关即偏好；点击在手势内补订阅。
3. **首次进入引导 + 工作台兜底**：老板/店长首次进入工作台弹一次引导（可跳过，跳过后「我的」页保留入口）；**应用内兜底提醒不依赖微信授权**：工作台 `onShow` 起每 30 秒轮询轻量接口（有新支付订单则顶部提示条、tab 红点、`wx.vibrateShort`），离开页面停止轮询，下拉可刷新。
4. 外部条件（不要假装做完）：真实订阅模板 ID。MOCK 下验证落 `notify_log`（`mock=1`）、偏好过滤生效、应用内提示可见。
5. 验收：老板、店长默认收到；核销员默认收不到；关掉某一项后不再落发送记录；授权额度用尽状态可见；轮询提示在模拟器里实拍。

### P1（小细节，读码发现）

**M-03 岗位说明与真实权限不一致**：岗位说明（`/m/site` 的 roleGuide）写「门店码、店员邀请码」是老板才有，但服务端和「我的」页对 `role >= 2` 都开放。以代码为准改文案：店长：核销员全部 + 订单、团期改价/名额/停售、对账单、评价回复、**门店码、店员邀请码（邀请进来的默认是核销员）**；老板：店长全部 + 店员角色管理。补一条断言让说明与 `role>=` 门槛同源，防再漂。

**M-04 通知一刀切发给全员**：见 M-02-1，另外 `notify_log` 要记收件人的角色，后台查看时能区分。

**M-05 下拉刷新有处理没开关**：`mini-b/pages/reviews/index.js` 写了 `onPullDownRefresh`，但页面 json 没开 `enablePullDownRefresh`，下拉无效；`me`、`order-detail`、`settlement`、`verify`、`proof` 五页既无处理也无开关。逐页补齐（`proof` 视情况）。

**M-06 员工管理的反馈**：老板改员工岗位后只 `fetchStaff()`，没有「已改为店长」的提示；停用员工二次确认缺失（误点即停）；员工列表缺最近活跃时间/加入时间。补提示与二次确认。

**M-07 改价后的可见性**：团期卡片显示「最近改价：谁、几点、¥旧→¥新」（版本簿 `master_data_version` 已有 `merchant-staff:` 记录，直接读）；老板和店长都能看到，核销员只读。

**M-08 订阅被拒的反馈**：现在拒绝只弹「未订阅」，补原因分流（用户拒绝 / 总开关关闭 / 模板未配置）和对应去处（去设置 / 稍后 / 联系平台）。

**M-09 工作台提醒状态条**：工作台顶部小条显示提醒状态（已开启 / 去开启），与「我的」同源。

### P2

**M-10 文案与小屏**：本轮新增文案跑 `npm test`（wording-guard、wxml-chain）；375 / 320 宽各页新增元素不溢出；触控区不小于 44px；灰字沿用已加深的 `#766b59`。

**M-11 证据**：隔离库 + 模拟器，老板、店长、核销员三套：改价（含大幅改价确认）、到单提醒开关三状态、工作台提示条、岗位说明新文案；每页一张 390px 截图，放 `docs/商户端权限与到单提醒-证据/`。

## 三、验收标准（Claude 将独立复核）

| 项 | 验收 |
|---|---|
| M-01 | 用老板、店长、核销员三个 token 打五个入口，结果与 §M-01-2 一致；改岗位后**同一 token** 立刻变化；大幅改价有二次确认 |
| M-02 | 迁移只增不改；默认偏好老板/店长=开、核销员=关；`notify_log` 随偏好变化；工作台轮询提示实拍；「我的」三种状态实拍 |
| M-03 | 说明文案与门槛同源断言通过 |
| M-05 | 五个页面下拉刷新实测可用 |
| 全局 | `cd api && npm test` 与全新隔离库 `npm run test:db` 退出 0；不得在 8080 的库上跑测试；迁移不得改旧文件 |

## 四、硬规矩（违反就退回）

1. 从最新 `main` 开分支，PR 提给我验收，**不要自己合并**；更新交接手册并在历史记录加一行。
2. **8080 上不得批量造单**（每笔订单都会产生存证并上真实链）。若需改库数据只用 SQL，先备份、先演练回滚、不得触发存证。
3. **本机 8080 是唯一的存证写入方**，不要在公网服务器（`api.1work.vip`）上开 `JOBS_IN_API`，不要对公网库做任何写入。
4. 小程序界面不得出现区块链用语；游客接口只下发白名单字段；金额存分、比例存 bp；新页面登记 `MINI_MAP`；WXML 里 `wx:elif/else` 不与 `wx:for` 同节点。
5. 提交前看 `git status` 和单文件大小；整库导出、`.sql` 备份、口令、密钥不得入库。
6. 测试里**不得再写「失败就打印并跳过断言」**（上一轮就是这样吞掉了转派接口的 9000）。
7. 做不完或做不到的项明说「未完成」和原因，不要写「已完成」；每项给「做了什么 + 证据」。
