## 3. 验收发现并已修复的缺陷

**M-01：改角色后「同一 token 立即按新角色」只对网关入口成立，接口内部的角色门槛仍按旧 token 角色判定。**

- 现象（隔离服务实测）：
  - **升权无效**：核销员被老板升为店长后，同一 token 改价仍返回 1003。
  - **降权漏网**：店长被降为核销员后，同一 token 仍能调用回复评价（过了角色门槛）、仍能拿门店码（返回 0）。
- 原因：网关里 `u.role = staff.role` 改的是 `authUser(req)` 返回的一个临时对象，`authUser` 每次都重新解析 token；接口内部再调 `requireUser(req)` 拿到的是旧角色。网关自带的 `manager` 正则只覆盖 `/supply /settlements /orders /invite /stats`，其余接口（回复评价、门店码等）全靠接口内部角色判定。
- GLM 的测试为什么没抓到：「升权即通」用的是本来就是店长的 token，没有测到"核销员 token 升权"的真场景；「降权即拒」只测了落在 `/supply` 的改价。
- 修法：`authUser` 对同一请求只解析一次并缓存在 `req` 上，网关覆写的角色接口内部能看到。补断言：核销员 token 升权后能改价；店长 token 降权后回复评价、门店码均 1003。
- 影响：这是一个安全缺陷——被降权或停用角色的员工在最长 7 天内仍保留部分旧权限，正是 M-01 要消除的。
