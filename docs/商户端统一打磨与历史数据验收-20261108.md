# 商户端统一打磨、演示样例与历史数据验收（2026-11-08）

## 实际问题与结果

旧工作台SQL只查当天，趋势固定七天；订单与核销记录固定最近50条，没有日期入口或翻页；库存接口仅返回未来与最近七天。历史数据还在，并非被删除。

- 工作台提供今日、近七日、近三十日及指定历史日，经营摘要与趋势按同一期间更新。默认近七日；当前待核销单独标明“当前”，不混作期间数。联调环境明确标注模拟支付不是实际扣款/到账。
- 订单支持服务端关键词、状态、支付日期和分页，不只对前50条做前端筛选；核销记录同样可按核销日和页码查历史。接口默认数组响应不变，原调用不带参数时保留默认50条；门店与员工行级权限始终在服务端。
- 库存按商品ID分组，同名不同商品不会合并；默认未来团期且全部收起，展开一个商品先见六个团期，可继续加载六个。关键词、未来七天/三十天、历史/全部日期、可售/余量紧张/截止取消可组合。合计余量排除过期和不可售团期；管理菜单保留名额、价格、早鸟与停售。
- 等级、勋章、可信凭证拆为三个页签，使用与工作台统一的纸面、墨紫、细边框样式。凭证对应已获得勋章的现有可信记录，不伪造新的身份凭证；排队、封存待确认、确认、重试、人工处理、已提交状态区分展示，只有实际确认才打确认标识。
- 订单、结算和我的统一卡片与摘要；结算默认收起账单，展开后保留完整分账、手续费、回单、异议、确认及逐单明细。确认对账不等于到账，状态口径未变。
- 我的及首页均提供可信凭证入口，老板/店长及平台运营原有改价权限不变。未新增员工或扩大权限。

执行脚本 `api/scripts/demo-merchant-orders-20261108.mjs` 默认预览；--apply要求本机8080、DB_NAME=wanderlust、非生产和未配置支付凭据，使用现有管理员密码环境变量。它只经业务接口创建、MOCK支付、核销和联调完成；无真实资金转移、短信或通知发送，无合约部署或密钥变更。重复执行新增订单0；授权样例同意记录也不重复写入。

新脚本 `api/scripts/demo-merchant-month-20261108.mjs` 默认仅预览，执行需明确开关、本机演示/隔离库、非生产、未配置支付凭据和管理员密码。先在隔离库验证两天八笔及重复执行，再备份演示库至 backup/merchant-month-before-20261108.sql 后导入。重复执行新增0。正常接口完成创建、MOCK支付、核销、完成、退款；没有手改金额、状态或积分余额。四条独立历史演示档案沿用对应商品摄影，导入后下架且团期截止，不挤占游客在售目录或制造可售余量。

只有本批新建样例的业务展示日期按模拟日回填，旧1488笔订单完整摘要保持一致。导入事件和审计注明真实导入时间与模拟业务日期；原始账本、既有日根和密钥摘要不变，新增积分双分录平衡且仍记实际导入日。没有回填旧存证时间、改根或伪造历史链交易。只读核验脚本 `api/scripts/verify-merchant-month-20261108.mjs` 逐单检查权益归属/数量、核销、退款、支付、库存与前后摘要。[核验汇总](evidence/merchant-polish-20261108/month-verified.json)、[样例订单](evidence/merchant-polish-20261108/month-orders.json)。

制造流水时验证了同商品同日唯一团期、联系人长度、有效期、成团和退款规则，沿用旧PC历史脚本会有孤立权益和不一致库存的风险，因此没有重跑旧脚本。库存分组补了每次六条展开以承载月度样例。经营流水按支付日且排除全额退款；订单退款筛选保留全退记录，核销按核销日统计。

本批完成态仍未生成结算单、实际打款或回单。既有结算生成器会一次扫入门店全部未结算完成单，不能为展示新流水而顺带结算旧单。本次保留原账单，真实商户AppID/真机、真实支付退款、协议和外部资料缺项仍见《剩余工作闭环与待提供资料》。
