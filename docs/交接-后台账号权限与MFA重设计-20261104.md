## 0. 一句话目标

把「后台账号」页重做成**账号 + 模块权限 + MFA 一站式管理**：

1. 每个账号能看/能办哪些**模块**可见、可配（超级管理员授予或收回）；
2. 每个**角色**有一套**默认模块**（超管可调整默认值）；
3. 账号页直接能**绑定 / 重置 MFA**（验证器 App、短信、邮箱），并能设**豁免 / 强制**；
4. 邮箱、短信验证码**真的能发出去**（目前只是 MOCK）。

## 3. 现状勘察（事实，已核对代码）

### 3.1 权限模型：只有「角色」，没有「按账号授模块」

- 角色：`super / ops / finance / review / risk / city_partner / readonly`（账号页 `ACCOUNT_ROLE_CN`，`pages/accounts.js:5`）；路由里还出现 `sre`、`dev`（`system/overview` 用），但**账号页不能创建**这两种。
- **菜单可见性**写死在前端 `api/admin/core.js` 约 L140–147 的 `access` 对象（角色 → 模块 key 数组）。`super` 与「表里没有的角色」不过滤。
- **接口权限**散在后端约 100 处 `requireAdmin(req, [...角色])`（`src/routes/*.mjs`）+ `ADMIN_ACTIONS`（`src/domain/admin-capabilities.mjs`，按钮级）+ 实体编辑 `entity-schema.mjs` 的 `roles` / `createRoles`。
- 前端按钮是否可点：`GET /admin/capabilities` 返回 `actions` 字典，前端用 `adminCan('xxx')`。
- 令牌：`requireAdmin` 校验 `token_epoch`；停用/改角色/改城市/重置密码会 +1，旧会话下一个请求即失效（`admin-accounts.mjs`）。**改模块权限也必须 +1。**
- 城市合伙人（`city_partner`）还有**行级隔离**（`scopeCity` / `scopeFilter`），与模块权限是两回事，**不能被模块授权绕过**。

### 3.3 MFA 现状

- 全局策略：参数中心 `admin.mfa.mode`（`off/optional/required`，默认 optional）；登录逻辑 `admin.mjs` `POST /admin/login`（约 L112–135）与 `POST /admin/login/mfa`。
- 账号表 `admin_user`：`mfa_secret / mfa_channel(totp|sms|email) / mobile / email / mfa_enabled`（V6），`token_epoch / must_change_pwd / note`（V44）。**没有「豁免 / 单用户强制」字段。**
- 验证码：`mfa_code` 表；`src/infra/mfa.mjs`（`sendCode` / `verifyCode` / `channelStatus`）。
- 已有接口（均 `requireAdmin(['super'])`）：`GET /admin/security/accounts`、`POST /admin/security/mfa/setup`、`POST /admin/security/bind-contact`、`POST /admin/security/mfa/disable`、`GET /admin/security/recent-codes`、`GET /admin/security/channels`；账号侧 `POST /admin/accounts/:id/mfa-reset`。
- 现有入口只在「安全中心」页（`pages/system.js` 的 `security()`）；「后台账号」页只有「重置 MFA」，**没有绑定入口**（这就是用户找不到的原因）。
- ⚠ **真实短信/邮件发送器是空壳**：`mfa.mjs` 的 `sendSmsReal` / `sendEmailReal` 直接 `throw`；`REAL_SENDER = { sms:false, email:false }`。当前所有短信/邮箱验证码都走 **MOCK**（只写库和控制台，在安全中心「最近验证码」可见）。#55 已保证「配了凭据也如实走 MOCK、不再静默丢码」。

### P0-B　模块权限：角色默认 + 超管可调整、可授予

**目标模型**

```
有效模块集合(账号) =
   super ? 全部
         : (角色默认模块集合 ∪ 账号单独授予) − 账号单独收回
```

**怎么做**

1. **模块清单做成单一数据源**：把 `core.js` 的 `NAV`（key / 中文名 / 分组）抽成后端 `src/domain/modules.mjs`（`MODULES = [{key, name, group}]`，50 项），前端通过 `GET /admin/capabilities`（或新增 `GET /admin/modules`）取得，**不再在前端写死**。保持 `key` 与现有 `NAV` 完全一致，防止菜单丢失。
2. **角色默认**：迁移新增 `admin_role_module(role, module, level)`，**用 §3.2 的表做种子**（用 `INSERT IGNORE` 的迁移脚本写入，保证与现状一字不差）。超管可在新页面「角色默认权限」编辑（对 `ops/finance/review/risk/city_partner/readonly/sre/dev` 逐角色勾选模块）。`super` 恒为全部且不可编辑。
3. **账号单独授权**：迁移新增 `admin_user_module(user_id, module, effect, granted_by, granted_at)`，`effect ∈ {allow, deny}`。账号页「权限」按钮打开弹窗：按 NAV 的 10 个分组展示全部模块，每组可「全选」，每个模块三态（继承角色 / 额外授予 / 额外收回），并显示「相对角色默认」的差异；保存时写审计（前后集合）、`token_epoch+1`。

### 运行与调试（本机环境的坑）

- 后台地址 `http://127.0.0.1:8080/admin-ui`；**演示账号 `admin / admin123`**（登录页「本地演示账号」）。
- **演示服务用 `JWT_SECRET=dev PASS_SECRET=dev` 启动，不要加载 `.env`**。原因：库里 `app_secret.VC_ISSUER_KEY` 是用 `.env` 的密钥加密的，而 40 条订单/商户联系电话是用 `dev` 派生密钥加密的——两把密钥的数据并存。`node scripts/secrets-key.mjs check` 能看到各自解不开的条目。统一密钥需要一次**有备份的重新加密**（脚本思路：用两把子密钥分别解开后写回，一个事务；见 `scripts/secrets-key.mjs` 的 `rotate` 实现），**未经用户确认不要动**。启动日志里 `VC_ISSUER_KEY 无法解密` 的告警是这个原因，已知且不影响演示。
- 启动方式（批处理，存成任意位置的 `start-8080.cmd`）：
  ```bat
  @echo off
  cd /d <仓库>\wanderlust\api
  set JWT_SECRET=dev
  set PASS_SECRET=dev
  "C:\Program Files\nodejs\node.exe" src/index.mjs >> server-8080.log 2>&1
  ```
  **从 AI 会话里直接启动的后台进程会在会话（甚至单轮）结束后被回收**；用 WMI 创建（`Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine='cmd.exe /c <脚本路径>'; CurrentDirectory='<api 目录>'}`）可以脱离会话，或让用户自己在终端里启动最稳。重启前先确认要停的是 8080 的那个进程（见下条），别误杀同机其他会话启动的 `src/index.mjs`。
- 前端 JS/CSS 由服务直接读磁盘，**改前端不用重启**，但浏览器会缓存脚本：验证前**强制刷新**（Ctrl+F5）；用 DevTools 时用 `reload` + `ignoreCache`。**改后端必须重启服务。**
- 自己造测试令牌：`jwtSign({ end:'admin', role:'super', name:'x' })`（`src/auth.mjs`，需与服务相同的 `JWT_SECRET`）；各 `test/*.mjs` 都这么做，可参考 `test/admin-orders-search.mjs`。
- 查哪个进程占 8080：这台机器 `netstat -ano` 的 LISTENING 行 PID 为 0，可对 8080 开一条保持连接，再看 `ESTABLISHED` 行里服务端那一侧的 PID。

## 8. 风险与注意

- **改权限最大的风险是「锁死自己」**：任何时候都要保证存在可用的超管；迁移与种子必须保证上线瞬间所有角色的有效权限与现状一致。
- **不要只改前端菜单**：这是现状的老问题（`readonly/sre/dev` 菜单泄露），新设计的核心是后端强制。
- 令牌失效：权限变更 `token_epoch+1` 会让对方被踢下线，弹窗里要提示「该账号需重新登录」。
- 参数中心里有些项需要**双人复核**；改 `admin.mfa.mode` 前先确认是否会绕过该机制（见 P0-A 第 3 点）。
- 演示数据里风控事件 `detail` 含 `demo:true`，页面显示「演示数据」小标；真实数据没有这个字段，别依赖它。
