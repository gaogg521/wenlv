# 商户双端与 PC 主体资源审批及平台运营工作台 · GLM 实施及 Codex 验收

日期：2026-11-20。GLM 负责实现和交付；Codex 负责独立验收。本方案覆盖登录页上的超级管理员、财务、城市合伙人、商户主体、景区主体，并增加平台运营演示身份。

## 1. 交付边界

- 商户可从商户小程序和 PC 新增、修改平台授权的本店资源；景区主体可从 PC 新增、修改平台授权的自有资源，并查看申请进度。主体提交后，所有启用的超管在后台收到通知。超管或拥有「主体资源审批」动作权限的平台运营均可逐单确认，批准才写入正式资源；退回必须填写原因。
- 平台运营使用现有 ops 角色和独立员工账号。支持按员工分配资源、内容渠道、订单售后三类职责，可组合配置。演示入口沿用现有本地演示机制。
- 首版通知使用站内收件箱、顶栏未读和审核人首页待审数。待审数与未读数分别计算，读过的待审单仍留在队列。
- 沿用现有主体绑定和商户小程序老板、店长、核销员角色。平台统一控制主体资源、操作及字段，渠道授权可分别收紧；最终权限取平台授权、主体范围、当前账号岗位及渠道授权的交集。两端的等价资源变更走同一审批状态机和正式写服务。核销、接单、履约及交易自动扣库存继续按现有业务规则。

**生效流程：保存草稿 → 提交审核 → 超管或获授权的平台运营确认 → 生效。** 一个有效批准即可生效，超管无需再次确认。审批权由超管按员工单独授予或撤回，普通运营默认无权审批，申请人不得审批本人提交的申请。

## 2. 能力与管辖范围

| 操作 | 商户主体 | 景区主体 | 平台运营 | 超管 | 财务／城市合伙人 |
|---|---|---|---|---|---|
| 新增商品、线路、团期或预约时段 | 本店提交 | 自营资源提交，须有已绑定经营主体 | 授权范围内维护平台资源、协助补件；获审批授权可确认 | 审批、平台配置 | 沿用已有查看与业务权限 |
| 修改商品、库存、价格、上下架 | 本店提交 | 自营资源提交 | 同上；获审批授权可确认主体申请，运营本人发起的敏感变更按内部权限办理 | 审批 | 同上 |
| 修改商户、景区公开资料 | 本商户提交 | 本景区提交 | 补材料、授权范围内维护；获审批授权可确认主体申请 | 审批 | 同上 |
| 创建景区主档、变更归属、商户或景区绑定 | 管理员办理 | 管理员办理 | 收集材料、跟进 | 校验并办理 | 沿用既有权限 |
| 查看申请、草稿、审计 | 本主体申请；草稿限创建人，提交后本主体授权账号可查 | 同左 | 授权业务范围内的已提交申请 | 全部 | 无新增权限 |
| 预审、退回、审批 | 可撤回自己的待审单 | 同左 | 预审、提醒补材料；获审批授权可退回、批准 | 退回、批准 | 无新增权限 |

景区与商品存在关联只代表展示或履约关系。景区自营商品必须用经过超管确认的经营主体绑定判定，现有数据模型若无法无歧义表示归属，首版只开放景区资料和资源维护，暂不开放景区商品写入。服务端按当前登录账号重新解析绑定范围。主体 ID、城市、经营归属由服务端确定，复合资源逐条验证归属。

超管在账号及权限页配置商户资源权限。配置至少记录商户、账号／岗位、渠道、资源、动作、字段组、授权人和变更时间。运营或商户员工不能自行扩大授权。服务端在编辑读取、保存草稿、提交及生效前校验。提交人被撤权后，旧申请保留历史，当前待审单暂停生效，由有权人员重提。申请和审计记录来源渠道。两端都可查同一申请及审批结果，仍按本主体及本人草稿规则过滤。

### PC 权威来源与双端同步

- PC 平台管理后台是授权管理入口，服务端保存的最新已发布权限是统一判定依据。PC 下发的开通、撤销、账号停用、岗位、主体及渠道范围同步到商户小程序和其他接入端。PC 商户界面同样执行平台下发的权限。渠道或本地缓存不可扩大授权。
- 服务端在每次敏感读取和写入时读取有效权限或验证权限版本，使用旧会话也无法继续操作已撤销权限。各端在登录、回前台、进入相关页面及收到权限变化事件时刷新权限快照；请求因权限变化被拒绝时立即刷新，关闭对应入口并明确提示。发布与同步带版本号，只有更新版本可以覆盖本地快照；离线时禁止提交，重连重新校验。
- 已审批生效的正式资源以 PC 平台后台所管理的服务端主记录为准。小程序使用同一正式记录和版本，不以端侧缓存或旧草稿覆盖正式值。两端发生版本冲突时先展示最新正式值及字段差异，保留草稿供用户重新核对后提交。PC 草稿和未获批准的申请不具有正式效力；从任一端发起且审批通过的变更进入同一正式记录。
- 订单与履约的实时业务状态继续使用业务服务记录，库存、占用和已售约束仍在生效时重验。权限和资源变更记录来源渠道、版本、发布人／审批人及时间，便于定位客户端同步问题。

## 3. 编辑字段及校验

复用现有资料编辑器与实体 schema。按「实体 × 操作 × 角色」在服务端定义可提交字段，禁止字段及嵌套字段在请求中出现即报错。遇到下列字段与现有 schema 不同，先映射已有语义，GLM 在交验单列出准确键名和遗漏。首版不为同义字段建第二份数据。

| 资源 | 主体可提交字段 | 校验及确认重点 |
|---|---|---|
| 商品／线路基础 | 类型、标题、副标题、标签、封面、图集、详情、行程、适用人群、费用包含和不含、购买与退改须知 | 按商品类别显隐必填组；商城直购无团期；到店预约使用时段；线路保留现行团期规则。预览游客端详情。上架校验图片、价格、可售资源与必填须知 |
| 商品交易字段 | 售价、已支持的规格、直购库存目标和调整原因、上下架申请 | 价格以分存储；校验早鸟价格及名额；库存不可突破已售、有效占用及现有库存规则；展示原值、新值和实际影响。费用、赠豆或补贴规则如影响平台支出，由超管单独配置 |
| 团期／预约时段 | 服务日期、起止时间、报名截止、容量、现有售价与早鸟价、集合信息、行程备注、关闭销售申请 | 日期顺序、截止时间、容量、价格按现有规则。已有订单时保护原履约承诺；调整时段、取消团期等影响已订游客的动作进入现有履约和通知处理流程，普通审批不得静默改变 |
| 商户公开资料 | 名称、简称、业态标签、标志及门头、介绍、地址及坐标、服务电话、营业时间、设施 | 校验格式、坐标、图片可用性。默认保留原商户主体、证照资质、银行账户、合同和结算配置 |
| 景区公开资料 | 名称、别名、等级、封面及图集、介绍、地址及坐标、开放时间、交通、游览须知、票种名称、门市价及适用说明 | 票种逐项展示差异。结算价和票务接口凭据不进入主体表单、申请快照或通知。景区城市、合作状态、合同、分成和内部备注归平台管理 |
| 停售／下架 | 目标商品或资源、原因、受影响时段、既有订单处理说明 | 已下单记录保持可履约；主体通过获授权端提交下架申请由超管或获授权运营批准。超管使用已有紧急停用机制时记录原因，保留未履约订单处理入口 |

库存、价格、时间、状态、退改政策、对外联系方式和地址在差异预览中标为重点。媒资使用已有上传机制，待审素材按草稿授权管理。已发布内容引用的媒体继续可用。合同、凭据、手机号等内部敏感数据按字段权限投影，避免从通知、差异、导出或列表泄露。

## 4. 页面与确认交互

1. **主体工作台**。显示「新增商品」「维护景区／商户资料」「我的变更申请」等当前身份可办入口。给出待审、退回、新近生效，并能直接过滤列表。资源列表同时显示正式状态和申请状态，例如「在售 · 价格变更待审」。
2. **资源编辑**。新增资源区分「新增商品／团期／预约时段」；修改基于当前正式版本。保存草稿后支持续编、预览和删除自己的草稿。提交弹窗展示对象、变更字段、影响、说明与附件，确认后锁定提交内容。新增尚未生效的商品可携带首批可售资源，合并校验和生效，避免出现孤立团期。
3. **资源审批**。供超管及获授权的平台运营办理。首页待办和通知深链到详情。按主体类型、对象、城市、操作、状态、重点字段、提交人和时间筛选。详情显示当前正式值、提交时基线、拟生效值及加载时最新的影响数据。图集、行程、票种和时段按项比对，显示新增、删除和移动。申请正文、预审意见、备注、历史决策各有作者与时间。
4. **确认与退回**。超管或获授权运营批准前，弹窗展示对象、重点变更、上架状态、已售和占用影响。改价、库存、上下架、履约安排和退改须知变更须明确勾选对应影响，并填写审批说明。退回和撤回必填原因。涉及正式主数据的申请逐单审批，确认期间按钮防重复提交。生效结果回到详情，可跳到正式记录。
5. **通知**。提交后给所有启用的超管创建站内待办通知，同时通知匹配当前业务范围且有审批权限的平台运营，同一事件按收件人去重。撤回后原通知可保留历史，同时移除待审任务。批准或退回通知提交人，包含结果、退回理由及链接。站内区分已读和处理完成；账号停用、授权变更后，详情和通知由当前权限重验。提交与通知落库应保持一致或可可靠补发。

## 5. 状态机、数据和并发

- 状态为草稿、待审核、已撤回、已退回、已生效。预审是意见和办理记录。撤回或退回后的再提交创建新版本并关联历史，旧审批记录保留。冲突时给出需要重新核对的字段和最新值，由主体重开或重提。
- 申请至少保存申请 ID、资源类型、操作、正式资源 ID（新增可空）、主体类型与 ID、城市、提交人、提交时间、基线版本、字段变更及快照、重点影响标记、状态、申请说明、附件、预审记录、审核人、审核时间、说明及生效后的资源 ID／版本。多资源申请记录依赖，保证同一事务校验并写入。
- 草稿不写正式资源表。确认事务锁定申请及受影响记录，复验申请状态、审批权限及其业务范围、主体归属、资源版本、库存和既有履约约束，再调用共享业务校验和正式写服务，记录审计与生效结果。提交和审批支持幂等；并发批准只生效一次。审批失败完整回滚，申请仍可追踪。
- 同主体、同资源默认一份待审单；仍可创建后续草稿。正式记录被平台或其他端更新后，拒绝以旧版本覆盖，尤其保护库存、价格、状态与时段。审批时不可用提交时的订单计数替代当前计数。新订单使用生效的新版本，历史订单及其价格、约定和结算记录沿用既有快照。
- 全量盘点 PC 和商户小程序的商品、快速改价、资料编辑、库存与时段、恢复版本、上下架及旧接口。主体方走申请或被拒绝，包含直接调用接口，不依赖隐藏按钮。审计保留提交、撤回、预审、退回、批准及正式资源差异。旧记录及已有角色兼容。

## 6. 运营权限与工作台

沿用 ops 及现有模块授权机制，补充动作级权限与服务端校验。用可组合的授权模板初始化，员工账号可进一步收紧。存量 ops 权限在迁移前列差异，避免升级后失去日常办理权限或取得额外资金权限。

| 职责 | 常规动作 | 须超管处理或确认 |
|---|---|---|
| 商品与资源 | 维护平台资源基础资料，协助商户和景区补件，检查可售资源，预审主体申请 | 改价、库存或团期调整影响已售履约、上架与下架、归属变更 |
| 内容与渠道 | 审核内容和约稿、处理举报、维护轮播、专题和活动草稿 | 公开渠道发布或撤下、涉及平台补贴和现金预算的规则 |
| 订单与售后 | 查订单及履约、客服备注、认领或跟进工单，按授权发起异常或退款申请 | 退款执行和资金动作走现有审批权限；账号、系统配置由超管管理 |

运营工作台显示本人和岗位队列，至少含待预审、待处理工单和内容待办，按当前授权显示并可直接办理。账号管理支持超管查看员工职责、授予／撤回权限、停用，以及记录授权原因。财务仍用资金工作台，城市仍按本城范围，五个原有演示角色登录路径均回归验证。演示运营账号只在本地演示环境出现。

## 7. GLM 实施顺序与交验材料

1. 先提交现状矩阵，列出PC 和商户小程序的各主体写入口、实际字段、正式写服务、可用审批及通知基础设施、景区自营归属证据、历史订单快照和现有运营权限。发现与本方案冲突时在交验单写明取舍。
2. 实现主数据审批模型、服务端授权与并发约束，再接主体编辑、资源审批及通知，最后接运营授权和登录工作台。前后端同批上线，确保新流程上线时两端旧主体直写入口同步收口。
3. 提交 PR、迁移与回滚说明、角色权限和字段对照、自动化测试结果、角色登录及每条关键流程截图或录屏、隔离库账号取得方式。交验使用隔离库。现有 8080 与公网部署等 Codex 验收后按发布安排处理。
4. GLM 完成开发和自测后交 Codex。Codex 使用独立会话和隔离库，核对申请、正式资源、游客读数、通知和审计，给出通过、条件通过或退回以及可复现证据。交验单不得记录账号密码、凭据或游客原始个人数据。

## 8. Codex 独立验收矩阵

| 编号 | 场景 | 通过条件 |
|---|---|---|
| AC01 | 演示与登录 | 原五个角色落点正常，运营入口在本地演示可用；生产无演示入口；运营真实账号按授权登录 |
| AC02 | 商户新增直购商品及首批库存 | 保存草稿和提交后，游客端不可查询或购买；审批后按批准值出现，可不选日期下单 |
| AC03 | 商户修改价格、库存、素材和退改说明 | 审批前仍为原版本；审核端逐项可比较；审批后新单按新价；原订单保持原价格和约定 |
| AC04 | 团期／预约变更 | 报名时间和名额校验生效；存在预约时防止取消服务或调整承诺；既有订单仍可核销 |
| AC05 | 景区改资料与自营资源 | 本景区资料审批后生效；关联商户资源无法提交；无明确自营归属时不出现该商品写入口 |
| AC06 | 站内通知及待办 | 每位启用超管及符合范围的授权运营收到一次通知，运营批准后超管仍可查看处理结果，点开直达；已读仍显示待审；退回或批准后提交人可查原因和结果 |
| AC07 | 撤回、退回和重提 | 撤回后旧申请不可批准；退回有原因；新版本可提交，旧版本、历史意见和决策完整 |
| AC08 | 权限与边界 | 主体账号、未获审批授权的运营、越权运营、财务和城市账号不能批准；获授权运营可在本授权范围批准并直接生效；审批人不能批准本人提交的申请；主体 A 无法提交或读取主体 B 的申请；禁止字段和两端旧写入口均被拦截；停用或降权会话即时复验 |
| AC09 | 并发和重试 | 双击、重放或超管与获授权运营同时批准只发生一次写入；待审期间并发下单或正式资源被平台调整导致冲突时保留最新资源；模拟写入失败无半成品 |
| AC10 | 运营三类职责 | 用三组权限真实登录，分别完成资源预审、内容处理、订单工单；交叉未授权动作服务端拒绝；资金与系统沿用职责边界；主体审批按独立动作授权 |
| AC11 | 状态和审计 | 新增、批准、退回、撤回、驳回后重提、旧版本并发冲突可追踪；通知、差异和导出无内部敏感字段 |
| AC12 | 回归与迁移 | 已有商品、团期、主体、订单和财务记录可读写；测试覆盖历史数据、授权撤销、回滚及公开读取；项目现有回归套件通过 |

| AC13 | 商户双端权限与审批 | 同一授权商户从两个端分别提交等价变更；任一端提交后可跨端查进度，批准前游客端不变；渠道、岗位、字段撤权后旧会话无法绕过；同一资源不能跨端重复挂单 |
| AC14 | PC 权限下发与数据冲突 | PC 开通、撤销及调整渠道权限后，小程序登录及回前台可见新权限；用旧会话提交立即被服务端拒绝；乱序权限响应不能恢复旧授权；PC 已生效正式值与小程序旧缓存或旧草稿冲突时，刷新到正式值并阻止旧版本提交，草稿可重新核对后再提交 |

**需要业务确认的边界**：景区已有自营经营主体和资源归属可直接按现有绑定实现，缺少数据则先交付资料审批；人工调整库存、改价、停售等主体资源变更，两端均按超管或获授权运营确认实施。若业务需要即时紧急停售，GLM 先提交触发条件、适用角色、通知与审计方案供负责人确认。
