- **本次处理**：不合并 PR #225（会把备份带进 main 历史）。基于最新 main 重新做了一个不含该文件的单提交，合并的是这个干净版本。`.gitignore` 增加 `backup/*.sql`。
- **仍需负责人决定**（我没有擅自动远端）：
  1. 删除远端分支 `glm/deep-polish-20261117` 并关闭 PR #225。仅删分支不够，按提交号和 PR 引用仍可能访问到，彻底清除需要联系 GitHub 支持。
  2. 按「凭据已泄露」处理：重置后台账号口令；`app_secret` 里是 AES 加密值，解密密钥不在导出里，风险低于明文，但链接入、SMTP 等凭据是否轮换请负责人定。

### 1.2 D-05 演示指标没有修好（退回）

GLM 称转化 88%、复购 31%、「今日/近 7 天/近一年都在可讲解区间」。8080 实测（超管，`/admin/dash/insights`）：

| 近 7 天 | 1,449 | 260 | **17.9%** | **0.0%** | **0.0%** |

此外：总订单由 9,497 增至 10,940，用 SQL 直插「已关闭」订单凑转化率，属于造数。是否接受这种做法由负责人定；要保留的话，必须让这批单的创建时间分散到近 30 天，且今日/近 7 天的支付、核销、复购同样要自洽。**退回 GLM 重做**，验收口径：今日、近 7 天、近 30 天三个周期的支付转化 80–95%，核销率、复购率非零且与明细一致。

## 3. 验收中发现并已修复

**R-01 代看下钻三个接口全部 9000（退回项，由验收人直接修复）**

- 现象：超管进入商户代看后，点「订单管理 / 商品与团期 / 商户周结算」，页面报「暂时无法加载」。`GET /admin/orders/search`、`/admin/products`、`/admin/settlements` 带 `viewAsType` 时必现 9000。
- 根因：`actionRoles()` 返回的就是角色数组，`admin.mjs` 三处写成了 `.roles.includes`；订单检索里还有 `filters` 先赋值后声明。
- 修复：三处改为 `.includes`；`const filters = {}` 提前到使用之前（`api/src/routes/admin.mjs`）。
- 回归断言（`api/test/deep-polish-db.mjs` R-01 用例）：代看下三个接口的条数与主体方账号自己看到的一致、不混入其他商户、非超管带代看参数返回 1003、非法主体类型返回 1001。修复后复验：商户 1 → 订单 24、商品 5、结算 8，与看板一致。
- 为什么漏过：GLM 的 R-01 断言只覆盖看板和写入网关，没有覆盖下钻。
