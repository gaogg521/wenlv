## R-05 岗位、授权、角色能力矩阵（方案）

### 现状盘点（同一件事在三个体系里有三套名字）

| 体系 | 取值 | 在哪定义 | 谁能看到 |
|---|---|---|---|
| 商户端岗位 `role` | 1 核销员 / 2 店长 / 3 老板 | `merchant_staff.role`（商户端登录 JWT） | 商户端四页按 role 裁剪 |
| PC 主体授权 | `merchant_partner` / `scenic_partner` + `admin_user.subject_type/subject_id` | V82，行级隔离在 `requireAdmin` 注入 | PC 侧栏按 `ROLE_DEFAULT_MODULES` |
| PC 平台角色 | super/ops/finance/review/risk/readonly/sre/dev/city_partner | `modules.mjs` 角色默认模块集合（V54 矩阵）+ 账号三态叠加 | `GET /admin/capabilities` |

三方互不相通：商户老板（role=3）不一定有 `merchant_partner` PC 账号；PC「后台账号」页看不到某人在商户端的岗位；商户端也不知道平台侧谁管自己。

### 方案（一页说明 + 两处落点）

1. **能力矩阵（唯一事实源）**：`api/src/domain/role-matrix.mjs` 新建，导出 `ROLE_MATRIX = [{ actor, side, scope, canView[], canDo[], notes }]`，条目约 18 行（9 个 PC 角色 + 商户端 3 岗位 + 游客端身份）。数据全部引用现有代码常量（`ROLE_DEFAULT_MODULES`、`ADMIN_ACTIONS`、商户端 role 判断），**不新造权限**，保证说明与实际一致。
2. **PC「后台账号」页新增「角色说明」页签**：渲染矩阵表格（行=身份，列=可见栏目/可办动作），数据来自 `GET /admin/role-matrix`（新端点映射 `accounts` 模块）。改动点：`admin/pages/accounts.js` 加 tab、`admin-modules.mjs` 一行映射、无迁移。
3. **商户端「我的」加「角色说明」卡片**：静态渲染（由 `/m/site` 下发 `roleGuide` 文本，模板 ID 走后台装修），按本人岗位高亮当前行。核销员只看到「我能核销、不能看账」一行说明。
4. **一致性保障**：加一条静态断言进 `test/admin-modules.mjs`——矩阵里每个 `canView[]` 必须是对应角色有效模块集合的子集、每个 `canDo[]` 必须存在于 `ADMIN_ACTIONS`，说明页与权限表漂移时测试红。

### 工作量与风险

约 0.5 天；无迁移、无权限变更（纯说明层）。风险点：`ADMIN_ACTIONS` 后续新增能力时忘记同步矩阵——由第 4 条断言兜住。

## A-03 游客端底部导航调整（方案）

### 现状与问题

五导航：首页 / 主题游 / 商城 / 旅豆 / 我的。旅行笔记（本阶段重点）只能从首页卡片与创作中心进入；新用户旅豆 0 时「旅豆」一级位价值低。

### 方案（推荐 A，附 B 备选）

**方案 A（推荐）：旅豆并入「我的」，新增「笔记」一级位**

- 导航变：首页 / 主题游 / 商城 / **笔记** / 我的。
- 「旅豆」入口移入「我的」资产摘要（A-02 已交付：旅豆余额卡可点），旅豆页本身保留为二级页；`MINI_MAP` 中 pages/bean/index 的「修改入口」描述同步改为「我的 → 资产摘要」。
- 新「笔记」tab：复用现有首页作品区数据源（feed 接口 `?tab=notes`），列表页 = 现有瀑布流组件搬入 tab 页；发布入口沿用创作中心。
- 影响面：
  1. `app.json` tabBar list 改 1 项（pagePath/图标 ×2）；
  2. `MINI_MAP` 新增 pages/notes/index 登记（test/miniapp-map.mjs 会把关）；
  3. 分包：笔记列表在主包（沿用首页作品区代码路径，无需新分包）；`custom-tab-bar`（mini-a 用原生 tabBar，无自定义组件）无影响；
  4. 装修配置：`site` 无 tab 相关配置，无需迁移；
  5. 深链兼容：原首页作品区保留（入口双份不冲突），旧分享路径不失效。
- 工作量约 1 天（页面复用为主 + 图标 2 张走 gen-tab-icons）。

**方案 B（保守）：不动导航，首页作品区加「全部笔记 ›」**

- 只加一个入口链接到笔记聚合页（新页面，同样登记 MINI_MAP）。工作量 0.5 天，但「本阶段重点」在导航层仍不可见。

### 建议

拍板选 A。理由：笔记是本阶段运营重点（UGC 小红书化三期已交付完整评论社交层），一级位曝光与「旅豆 0 价值」问题一次解决；且方案 A 的全部改动点都在现有验收体系覆盖内（MINI_MAP / wording-guard / 走查脚本）。

## B-05 商户端「游客笔记」（方案）

### 现状

PR#213 打通笔记与景区/线路双向关系，但商户端看不到游客写本店线路的笔记。

### 方案

1. **数据口径（只读）**：本店商品（`tour_product.merchant_id = 本店`）关联的、`content_note.status=2`（已发布公开稿）的笔记，按发布时间倒序前 20 条。**五种夹具对齐 PR#213**：已发布公开稿可见；私密、审核中、驳回、下架一律不出现（服务端 WHERE status=2 硬过滤，不依赖前端）。
2. **接口**：`GET /m/notes`（merchant.mjs，返回 id/标题/封面/摘要/发布时间/作者昵称/关联商品标题；**不下发** body 富文本与内部字段）。映射 `admin-modules.mjs` → `orders` 模块（商户工作台数据线）。
3. **入口**：工作台「游客的声音」评价面板下新增「游客笔记」区块（显示最新 3 条 + 「查看全部」），全部列表复用 reviews 页结构新建 `pages/merchant-notes`（或并入 reviews 页顶部 tab——推荐后者，少一个页面少一条 MINI_MAP 登记负担）。
4. **红线**：不暴露私密内容（status 硬过滤）；文案过 wording-guard（笔记标题来自 UGC，展示层原样渲染 rich-text 前先 `plainText` 化）；不出现「审核中/驳回」等内部态。
5. **验收路径**（批准后实施）：五种夹具各建一条 → 商户端只见已发布公开稿；私密/驳回/下架三种在接口层直接查不到（断言进 deep-polish-db）。

### 工作量

约 0.5 天（接口 1 个 + reviews 页加 tab）。无迁移。
