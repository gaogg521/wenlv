## 5. 需要业务确认的边界(方案§8 尾栏)与取舍

1. **景区自营商品写入**:首版不开放(现有模型无独立绑定表);V95 已预埋 `selfrun_merchant_id`,业务确认归属口径后可放开。
2. **商户小程序新增商品表单**:mini-b 现无商品档案编辑页;本次交付供给变更(价/名额/停售/恢复/早鸟)申请+跨端进度,商品新增以 PC 为主体端入口(AC02 由 PC 验证)。
3. **mini 即时改价改申请制**:原 M 系列直写入口全部转"提交审核",确认交互保留;旧断言已同步更新(merchant-notify-round M-07)。
4. **紧急停售触发条件**:沿用现有紧急停用机制(超管);如需"主体即时紧急停售"通道,按方案需先提交触发条件/角色/通知与审计方案,未擅自开放。
5. **PC 团期级快速改价**:无独立页(改价走团期编辑器),收口在申请制内。

## 6. 环境敏感点与既有数据发现(非本次代码回归,交 Codex 复核)

1. **演示库账本漂移(真实发现)**:`wanderlust` 与 `wanderlust_qa_fix1106m` 的 2026-11-07 日根 leaf_count=6,但当日账本已有 78 行——日根封存后账本继续增长(I1 不一致)。属演示环境历史数据问题,建议负责人安排账本巡检/补封;QA 库通过对齐 leaf_count 元数据放行(不动根哈希)。
2. **密钥纪元混杂**:演示库的加密手机号/联系电话存在多个 PASS_SECRET 纪元的密文,部分历史密钥已丢失无法解密(scripts/secrets-key.mjs check 可复现);SMTP 凭据解不开是手册 §2 在案的既有分裂。
3. **WX 凭据**:配置 WX_APPID/WX_SECRET 时,member-badge 测试的非 mock code 走真实微信必失败——QA 配方需 unset(生产不受影响)。
4. **chain-contract-e2e**:需全新 mock 合约状态(服务重启后单独跑即绿);与 demo 库链历史共存时需 CHAIN_ENDPOINT=1 口径。
5. **演示环境改动披露**:验证过程中将 `wanderlust`(演示库)admin 口令重置为 .env 的 ADMIN_INIT_PASSWORD(原值不再可用的状态下保持可登录);QA 库口令一律按上述配方统一。
