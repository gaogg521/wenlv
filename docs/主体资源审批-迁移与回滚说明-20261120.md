## 3. 回滚方案

### 3.1 代码回滚(应用层)
- 回滚到上一版本(merge-base 800212a)即恢复旧直写行为:PC 主体直写恢复可用、mini 供给恢复即时生效。V94-V96 新表留在库中(无害,旧代码不读写)。
- 建议顺序:回滚代码 → 重启服务 → 观察 `/c/health` 与商户端改价链路。

### 3.2 数据库回滚(仅在需要彻底清除时执行;默认不执行)
```sql
-- 回滚脚本(手工执行,迁移框架无 down;顺序先收件箱后主表,避免外键/引用)
DROP TABLE IF EXISTS platform_inbox;
DROP TABLE IF EXISTS subject_resource_request;
DROP TABLE IF EXISTS subject_perm_grant;
DROP TABLE IF EXISTS admin_user_action;
DROP TABLE IF EXISTS subject_perm_version;
ALTER TABLE scenic_spot DROP COLUMN selfrun_merchant_id;   -- V95
DELETE FROM admin_role_module WHERE updated_by = 'V94-migration';  -- V96 补行(只删迁移补行,不动既有行)
DELETE FROM schema_migration WHERE version IN ('94','95','96');
```
- 回滚前如需保留审计痕迹:先 `mysqldump` 上述 5 张表留档(`subject_resource_request` 内含申请/审批历史,属业务凭证)。
- 回滚不影响:`master_data_version`(版本簿,审批生效写入的记录保留,旧代码可读)、`audit_log`、`attest_event`(商品变更存证,链上指纹不受影响)。

### 3.3 回滚后的遗留数据口径
- 已生效的申请对应正式资源已是新值(商品/团期/库存/资料),代码回滚不会自动还原——如需还原用 PC 既有「版本历史 → 恢复」(仅 super)或再次编辑。
- `platform_inbox` 中未读通知随表删除一并消失(站内通知,无外发)。
