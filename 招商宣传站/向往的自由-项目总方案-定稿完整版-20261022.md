# 第一部分 战略与产品

## 1. 项目定位

「向往的自由」= Tourism Web3 OS（文旅生态操作系统），上海璟宬文化发展有限公司主体。三层架构：

| 层 | 定位 | 承载 |
|---|---|---|
| A 层 | 会员消费生态 | 游客获客、消费、旅豆、复购 |
| B 层 | 贡献经济共同体 | 推广服务商、创作者、商户、城市合伙人协作与价值分配 |
| C 层 | 全球 Web3 网络 | 跨区域身份互认、权益互通（P3+，境内外物理隔离） |

共同底座：真实文旅交易与履约 + 订单、支付、结算、积分、凭证、风控、数据。

**Web3 双层口径（定稿 D6）**：微信内旅豆=积分体系，全站不出现链/Web3/NFT 字样；生态对外（H5/宣传站/政府与景区 BD）旅豆=「向往自由链」链上权益凭证，正面表述；后端联盟链存证 P1 真实上链。红线（不对应股权/Token、不按层级计酬、境内外隔离）保留在服务协议与服务端。

## 2. 角色 × 端 × 数据一致性（核心章）

### 2.1 四种业务角色

| 角色 | 层 | 是谁 | 核心动作 |
|---|---|---|---|
| 游客 | A 层 | 消费者 | 浏览、下单、支付、核销、赚豆、发笔记、升级 |
| 推广服务商 | B 层 | 导游、店员、大学生、司机等（"用户群里：导游、任何人"） | 发推广码/海报、看推荐客户、看推广服务费、提现 |
| 商户 | 履约层 | 景区/酒店/餐饮/体验供应商及其店员 | 接单、扫码核销、库存/加场/调价、对账、结算确认 |
| 平台运营 | 管理层 | 公司运营/财务/审核/风控/城市合伙人 | 驾驶舱、商品与订单管理、审批、结算复核、风控 |

两个衍生身份（不是独立角色）：**创作者** = 游客在 A 端的身份延伸（笔记/约稿任务/作品）；**城市合伙人** = PC 后台里的一个 RBAC 角色（看分城经营数据、佣金）。

### 2.2 三个客户端及其使用者

| 客户端 | 使用者（角色） | 承载模块 |
|---|---|---|
| **小程序 A**（游客主站） | 游客（主身份）；推广服务商（"我的→推广中心"）；创作者（身份延伸） | 首页/主题游/旅豆/我的 + 推广中心 + 创作中心 + 电子凭证 |
| **小程序 B**（商户端） | 商户老板、店长、核销员（一个商户多店员） | 工作台/扫码核销/订单/库存/对账结算/店员管理 |
| **PC 运营后台**（Next.js） | 平台运营、财务、审核、风控、城市合伙人（RBAC 分角色） | 驾驶舱/商品/订单/审批/参数中心/结算/风控/存证/审计 |

要点：**角色不是账号隔离，是权限上下文**。一个自然人用同一个微信身份（unionid）可以在不同端持有不同角色；A 端内"游客↔推广服务商"切换只换功能视图，不换身份、不换数据。

### 2.3 数据一致性模型：一个身份、一本账、一套订单

```
                    ┌──────────────────────────────┐
                    │   MySQL 单库（事实来源）        │
                    │                              │
  user_account ──── 1 行/自然人（unionid 打通 A/B 小程序）
       │                                          │
       ├── bean_account ── bean_ledger            │  旅豆：全局一本账，
       │    （每个自然人唯一户，双分录）              │  A 端赚的豆 B 端场景同样可抵
       │                                          │
       ├── orders / travel_pass / pass_code       │  订单与凭证：游客端写入与展示、
       │    商户端核销读写同一行                    │  商户端核销、后台审计，三方同源
       │                                          │
       ├── promoter / attribution / commission    │  推广归因跨端：A 端扫码 →
       │                                          │  订单携带 scene → 佣金自动入账
       └── merchant / settlement                  │  商户结算与后台复核同源
```

一致性由四条机制保证（不是靠前端，是靠服务端）：

1. **单库事务**：一个自然人、一张订单、一本账在同一个 MySQL 实例，跨模块写操作（下单+占名额、核销+订单状态、发豆+分录+预算池）都在同一事务。
2. **状态机唯一写入口**：订单、核销、结算只有一条代码路径可改状态（`OrderStateMachine.fire` 等），三个端都是它的调用方，不存在"商户端改商户端的副本"。
3. **乐观锁 + 幂等键**：余额、名额、核销码用 `version`/唯一约束防并发；支付回调、离线补登、佣金结算重放无害。
4. **日终对账**：账本试算（Σ分录=余额）、订单-结算聚合、收付通账单三方核对，差异 P0 告警。

### 2.4 数据读写矩阵（核心表 × 角色）

| 数据 | 游客(A) | 推广服务商(A) | 商户店员(B) | 运营(PC) |
|---|---|---|---|---|
| user_account | 本人只读 | 本人只读 | — | 脱敏只读 |
| orders | 本人读写 | 推荐客户订单只读（脱敏） | 本商户只读 | 全量读写（审批） |
| travel_pass / pass_code | 本人展示码 | — | 核销（写 verification_log） | 查询/统计 |
| bean_account / ledger | 本人只读 | 本人（佣金入账自动） | 商户旅豆额度只读 | 预算池读写（审批） |
| tour_product / session | 只读 | 只读 | 本商户团期读写 | 全量读写 |
| settlement / dispute | — | — | 本商户确认/申诉 | 复核/裁决 |
| rule_config | — | — | — | 参数中心读写（双人复核） |

原则：**每个角色只看到自己权限上下文内的数据投影，底层永远是同一行数据。** 商户看不到游客手机号明文（脱敏），推广商看不到客户身份（只有归因统计），运营看不到资金池（收付通直付）。

## 4. 业务规则定稿与参数中心

### 4.1 定稿总表（数字进 rule_config，页面可改，代码零硬编码）

> **规约**：代码只允许 `ConfigService.get(key)` 取值；**可硬编码的只有结构**（枚举、状态机、公式形状），**一切数值/比例/阈值/天数必须来自参数中心**。单元测试断言从 rule_config 注入同一来源，断言公式正确性而非数字本身；另设"基准快照"断言防止无意识改参。

**旅豆（bean）**

| bean.global_cap | ¥600,000/年（折豆） | 固定发行总量，严禁超发 |
| 任务/内容奖励 | 任务 +200；笔记推荐 +50（周上限 500）；剧本 80/50/20 | 三结局价值观权重 |

**推广服务商（D2 定稿，替代 demo 五级）**

| 档位 | 条件（滚动 90 天有效成交） | 费率 | 权益 |
|---|---|---|---|
| 基础 | 注册+实名+签约 | 5% | 推广码/海报/明细 |
| 优选 | ≥¥10,000 | 8% | +内测优先、月度周报 |
| 金牌 | ≥¥50,000 且评分≥4.5 | **12%（封顶）** | +专属对接、线路共建 |

佣金基数=实付-豆抵扣；过退款期计入；降档次月生效；提现 ¥100 起微信商家转账、单日 ≤¥5,000。

**会员等级（D4）**：成长值 = 已核销订单实付（1 元=1 分）+ CS×10（月结）；阈值 **0/2,000/10,000/50,000** = 探索者/旅行家/城市探索官/环球探索家；年度滚降一级。权益逐级解锁（优先购/隐藏剧情/共建投票/年度免费线路）。

**结算（D11）**：退款观察期 7 天；佣金 T+7；商户周一出周账单、确认后 T+1 分账。五口径恒等式 `订单额=履约+服务费+推广费+权益预算+留存毛利`（CHECK 约束）；超支从留存毛利扣；协议调价全链重算。

**成本控制（D12）**：超支审批 ≤¥3,000 运营总监 / ≤¥8,000 财务 / >¥8,000 或连续两期破线 CEO；熔断 25%（停新增投放不停存量核销）；预测三态 25%/50%。

**经营基线**：3,000 单/¥399/20%/9%/2%/18 万 → 结余 −72,270、平衡 5,013 单（保持亏损结论）；四条反解路径进测算器默认值。

**补充业务规则（定稿）**：

- **未成团处理**：团期 `depart_date` 前 48 小时仍未达 `min_go` → 自动取消 + 全额原路退款 + 订阅消息通知；游客可免费改签同频道其他团期（同价）。
- **退改规则**：平台默认梯度（出发前 7 天免费 / 3–7 天收 10% / 72h 内收 30% / 出发后不退），商品可在 `rich_desc` 覆盖平台默认；退款走 60→70 状态机。
- **初始维度配置**：`city_code` 初始 = **310118（上海青浦·朱家角）/ 320508（苏州·姑苏）**；`channel` 初始 = `main`；第二频道 `yoga` 随 P2 矩阵分叉启用。

### 4.2 参数中心（后台页面，数字全部可改）

数值不再"写死"——**参数中心是 PC 后台的一个正式模块**，任何业务数字的修改都走它：

**功能设计**

1. **分组浏览**：按域分组（旅豆/会员/推广/订单/结算/成本控制/风控/渠道矩阵），每参数显示 key、当前值、初始值、memo、最近修改人/时间。
2. **修改审批（双人复核）**：编辑提交 → 另一角色审批 → 生效。敏感分组（旅豆发行、佣金费率、审批阈值、global_cap）强制走审批，其余可配置为直接生效；连续修改同一 key 两次以上自动升级审批。
3. **影响预览**：提交时自动回溯试算——如改 `bean.order_rate` 10%→8%，页面立即显示"按近 30 日订单回溯，月发放量、预算池消耗、各单位经济指标的变化"。改 `promoter.rate_bp` 显示各档服务商收益变化与毛利率影响。
4. **版本历史与回滚**：每次变更生成版本（旧值/新值/提案人/审批人/生效时间），支持一键回滚到任意历史版本。
5. **审计**：全量写入 `audit_log` + `config_history`；生效后自动触发相关回归测试集（金额公式类用例）。

**表结构（新增两张）**

```sql
CREATE TABLE config_history (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  cfg_key      VARCHAR(48) NOT NULL,
  old_value    JSON NULL,
  new_value    JSON NOT NULL,
  proposer     VARCHAR(32) NOT NULL,      -- 提案人
  approver     VARCHAR(32) NULL,          -- 审批人（双人复核）
  status       TINYINT NOT NULL DEFAULT 0, -- 0待审 1生效 2驳回 3回滚
  reason       VARCHAR(256) NULL,         -- 修改原因（必填）
  effective_at DATETIME(3) NULL,
  created_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  KEY idx_key (cfg_key, id)
) ENGINE=InnoDB COMMENT='参数变更历史（版本+审批+回滚依据）';
-- rule_config 增列：group_name VARCHAR(24)、sensitive TINYINT(1)（强制审批）、updated_version BIGINT（乐观锁）
```

**API**：`GET /admin/config?group=`、`POST /admin/config/proposal`（提交修改）、`POST /admin/config/approve`、`POST /admin/config/rollback`、`GET /admin/config/history?key=`、`POST /admin/config/preview`（影响试算）。

**注意**：参数中心改的是**运行参数**；凡涉及结构的改动（如新增返豆来源类型、新增会员等级）仍是代码变更，走正常研发发布——参数中心不背架构演进的锅。

### 5.2 六条架构原则

1. 单体模块化起步，包边界=未来服务边界；2. 数据库是事实来源，链是审计锚点；3. 钱豆佣三账本双分录；4. 全链路幂等键；5. Web3 双层口径；6. 多主题小程序矩阵就绪（`channel` 一级维度，unionid 打通，旅豆全局一本账；第二个小程序=瑜伽，纯配置分叉）。

## 7. 后端服务设计

### 7.1 分层与事务

### 7.5 发豆链路与定时任务

**发豆链路图（对应方案 §9 生命周期：预算批准→发放→兑换→核销结算）**

```
订单 50(已完成) 事件
      │ (观察期7天结束, 退款风险出清)
      ▼
┌─ beanWorker ──────────────────────────────────────┐
│ 1. 幂等键检查 bean:{order_no}                       │
│ 2. 批次预算校验: granted+X ≤ total+returned         │
│    └ 不足 → 按 rule_config 走审批或拒绝              │
│ 3. 全局总量校验: Σissued+X ≤ global_cap             │
│    └ 触顶 → 熔断发放并告警(严禁超发红线)              │
│ 4. 同一事务:                                        │
│    bean_ledger 两行分录(贷:用户户 / 借:预算池户)      │
│    + bean_account.balance + bean_budget.granted     │
│    + bean_global_cap.issued_sum                     │
│ 5. 写 attest_event(账本锚定队列)                     │
└───────────────────────────────────────────────────┘
```

### 7.6 存证（链上锚定）

```
 MySQL(RDS) 事实来源
   │ 业务事件: 订单完成/积分发放/凭证签发/核销/退款冲正/结算生成
   ▼
┌─ 存证服务 AttestationService ────────────────────┐
│ P0: NoopClient(只打日志, 工程不等链)               │
│ P1: 链数根适配器 ChainShuGenClient                 │
│  · 异步: 业务事务提交后入 attest_event 队列          │
│  · 批量: 每小时将事件哈希聚合成 Merkle 根            │
│  · 上链: attest_batch → 链数根 → 回填 chain_tx_ref  │
│  · 容错: 链故障业务照跑, 事件滞留待打包, 恢复后补锚    │
└─────────────────────────────────────────────────┘
   │ 上链的只有: 哈希指纹 + 时间戳 + 主体标识 + 签名
   │ 不上链的:  全部业务数据(实时查询/分页/统计都在 MySQL)
   ▼
验证接口(admin+open): 输入订单号 → 链上锚定信息 + 本地哈希比对
  → 给景区/城市合伙人/监管讲"一网可信"的落地凭证
```

接口 `AttestationClient` P0=Noop，P1=链数根适配器。小时级 Merkle 打包上链，失败重试+告警，链故障业务照跑事后补锚。验证接口：输入订单号→链上锚定信息+哈希比对（景区/监管可讲"一网可信"）。

## 12. 安全 · 内容安全 · 隐私

- 脱敏：手机号/身份证 SM4 加密 + HMAC 检索列；后端返回即脱敏（`138****6621`），日志脱敏 converter。
- 内容：msgSecCheck 同步 + mediaCheckAsync 异步 + 人工队列；P0 笔记只读。
- 反作弊：设备指纹聚类、一人多号领豆检测、核销地理跳跃、佣金异常（同 IP 高频新客）→ risk_event；作弊单不进推广窗口、豆回收。
- 隐私：小程序隐私保护指引逐项声明；getLocation 仅打卡功能启用后申请；授权可撤回（user_privacy_consent）。
- 备份：RDS 自动备份+binlog，保留 30 天，每月恢复演练；COS 版本化。
