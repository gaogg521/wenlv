## 三、已定决策（不要推翻）

1. **测算器必须是亏损的。** 方案 §8.2 原值：3000 单 / ¥399 / 20% / 9% / 2% / 固定 18 万 → 结余 **−72,270**，平衡 **5,013 单**。曾经被改成盈利，已回滚。亏损是方案的诚实结论，靠"四条路径"讲怎么补，才叫商业说服力。
2. **旅豆不可提现、不可交易、不承诺升值。** 这是合规红线，任何页面文案都不能松口。
3. **CS 不对应股权、不对应 Token。** 页面上必须明写。
4. **不按层级计酬。** 合伙人分润只挂直接贡献，不挂下线圈层。
5. **境内外隔离。** 境外走稳定币 + 法币双轨，与境内积分账本物理隔离。
6. **所有插画程序化生成。** 不允许引外部图片/字体/JS。`sceneSVG()` 13 类场景在 `src/p4b.html`。
7. **只改 `src/`，不改产物。** 产物每次构建都会被覆盖。
8. **【v1.3 新增】支付完成后绝不切换身份。** 赵老师明确指出"支付后直接进入合伙人页面、且无法返回、支付成功弹合伙人界面"三重不合逻辑。铁律：`afterOrder()` 只允许 `renderBase()` + `pushOrderDetailPage()`，**禁止 `setEnd('partner')`**。四端联动改由"收益去向面板"呈现，而不是把用户拽到别的端。
9. **【v1.3 新增】页面栈是唯一返回路径。** 任何"新开一页"的交互都必须能一次返回到来源页。禁止 `clearStack()` 式跳转；筛选/排序切换一律原地重绘（`repaintCurrentPage`），不压栈。
10. **【v1.3 新增】业务按钮必须改真实状态。** 约稿任务、订单、商品、库存等一律有状态机 + DOM 真实刷新 + 持久化。**禁止只弹 toast 的假按钮**（`（演示）` 类 toast 已全库清零）。

## 四、已走过的弯路（新助手别重犯）

| 现象 | 真因 |
|---|---|
| 全站点击全失效、控制台不报错 | `<style>` 标签没闭合。先跑 `build.py` 看配对结果 |
| 多条隔离红线挤成一行互相覆盖 | `.kvs` 是"一行 label+value"，不是容器。多行就写多个 `.kvs` |
| 白卡片里进度条看不见 | `.prog` 是白底白条，要加 `.prog.on-light` |
| 缩略图整体发灰 | `.imgwrap` 自带暗角，加 `.flat` |
| 标题里的图标被推到两端 | `.sec-title` 是 `space-between`，图标要包 `<span>` |
| 环形图被压成竖条 | 必须写死 `width/height/flex:0 0 auto` |
| 内联 onclick 报 `ni is not defined` | 模板字符串的局部变量不会成为全局变量，要拼字面量 `onclick="f(${ni})"` |
| `pushCategoryPage('all')` 语法错误 | sortKey 缺引号包裹，且**每个分类 chip 都要带上当前排序**，否则点一下全线失效 |
| 点 10 次分类，返回键要按十几次 | 切换分类/排序不该压栈。检测栈顶标题相同则原地重绘 `.page-body` 并保留 scrollTop |
| 筛选 chip 点了"没反应" | 只重绘了列表容器，chip 的 `.on` 类没更新 → 改用 `repaintCurrentPage(fn)` 整块重绘 |
| 旅拍页"平台收购"被当 0 豆兑换成功 | 非豆数定价项混进了豆数抵扣逻辑，扣豆要加 `/\d+\s*豆/` 守卫，非豆项走投稿流程 |
| 走查误判"状态没变" | 选择器用了 `.page.in`，动画未完成时抓到栈底页。**统一用 `#pageStack .page:last-child`** |
| 走查误判"排序切换无响应" | 快照只比 `innerHTML.length`，切排序档只改 class、长度不变。快照须含 class 与元素顺序 |
| 满屏"无响应"误报 | 已选中项（`.chip.on`）点击本就幂等，扫描时要显式跳过 |
| 本地构建 368,297，云端 371,073 | 行尾差异。`build.py` 已锁定 `newline='\n'` |
| 云端上传出了个空节点 | `import-local-file` 要 `confirmKey`+`taskId`；重复上传会新建节点，**要复用节点原地提交** |
| 跑 node 工具报 `SAFE_DELETE_FAIL_CLOSED` | PowerShell 的删除被安全 shim 拦截；node 工具命令前加 `NODE_OPTIONS=""` 绕过 |
| 搜索框每打一个字返回键就多按一次 | `oninput="pushSearchPage(this.value)"` 每次输入都压栈，改成 `filterSearch(this.value)` 只重绘结果区 |

## 十三、v1.4.1 深挖bug：预算池口径体系统一（2026-10-19 晚）

背景：v1.4 六大引擎可玩化后，做了一轮现有 9 套工具都没覆盖的**跨页数据一致性**深查，揪出 4 个真 bug（1 个口径体系统错误 + 1 个业务负数 + 1 个演示链断裂 + 1 个工具假阳性）。

### 修了什么

1. **预算池口径混乱（最严重）**：`DB.admin.budget` 三字段曾被三种解读——引擎页把 `used`（已核销）当"已用/已发行"、把 `issued` 当"可承受贡献利润"；风控页把 `issued` 当"已发行"；支付流 `applyOrder` 发放时 `issued += earn`。同一份数据三个口径，投资人细看必露馅。
   - 统一语义：`total`=已批准营销预算 / `issued`=已发行额度 / `used`=已核销，剩余可发 = `total - issued`
   - 改动：`rwCap / rwIssue / rwBody / rwBook / stSplit / stRefund` 六处；删掉 `rwIssue` 里 `issued = max(issued, used+20000)` 的暗桩
2. **四本账与预算池同口径**：发行账=已发行、核销账=已核销、回收账接新增计数器 `DB.engine.recycled`（回收动作真实累加，种子 3,200）；核销账种子 96,400 → 189,400 对齐 `used`
3. **结算闭环**：分账时预算池注入 5% 占用发行额度，退款原路回收，split→refund 净变动为 0
4. **对账净额负数**：全额退款订单原算出「应结 -¥71」，改 `net = max(0, 履约 - 退款)`，全额退款应结为 0
5. **网关阈值失效**：两个「接近阈值」API 实际使用率 66.5%/87% < 90% 判定线，在线调试永远打不到热接口、配额扩容链断；种子调至 90.6%/94.5%
6. **enginetrace 工具自身 bug**：一条断言写 `DB.budget.used`（字段不存在）→ `ev` 返回异常对象恒 truthy → 永远 PASS，已蒙混一整轮；另两条把旧错误口径写进断言，一并修正

## 十四、v1.4.2 体验打磨：tab 统一 / 灵动岛 / Web3 页（2026-10-19 晚）

## 第二十章 · v1.8 权益预留池超支审批 + 协议变更单（成本控制闭环）

**时间**：2026-10-20 12:45–13:20
**触发**：用户指出「发行→持有→核销→对账→分账」已全链闭环，但**超支只有建议没有动作流——谁批、批多少、超额怎么办是空的**；且「入园名额 ¥34→¥30 重谈」还只是文字，要求做成商家端可发起、平台端可审批的协议变更单。

### 1. 为什么必须补这一层（业务判断）

v1.7 把权益成本算清楚了，但**成本失控时没有决策出口**，这在真实运营里等于没有成本控制：
- 缺口 ¥7,594 写着「从营销预算调剂」，但**谁有权批、批多少、批完钱记哪个科目**都没有定义；
- 「¥34 → ¥30 重谈」是写在建议里的文字，商户端没有发起入口、平台端没有审批动作，谈完了系统里还是老价。

结论：**账算得清 ≠ 成本控得住**。成本控制的三个必备件是授权、额度、熔断。

### 2. 设计决策一：分级授权（谁批）

| 审批人 | 限额 | 适用范围 |
|---|---|---|
| 运营总监 · 李思远 | ≤ ¥3,000 | 营销预算科目内调剂 |
| 财务负责人 · 周颖 | ¥3,001–8,000 | 跨科目须财务联签 |
| CEO · 赵董事长 | 终审（无上限） | 超 ¥8,000 或连续两期破熔断线 |

实现为纯函数 `overrunNeed(amt)`，视图自动高亮当前归口。当前申请 ¥7,594 → 落在财务负责人；历史单 ¥2,140 → 运营总监权限内。

**决策理由**：不做成固定角色，是为了演示「金额决定审批人」这条真实规则 —— 超过额度自动上收，这本身就是一套防舞弊机制。

### 3. 设计决策二：部分批准 → 余量自动升级（超额怎么办）

这是本轮最关键的设计。审批不设「全有或全无」，而是允许**部分批准**，剩余金额**自动生成升级单**转上一级：

```
申请 ¥9,000 → 财务负责人批 ¥5,000（其权限内）
            → 余 ¥4,000 自动生成 OV-T-02，标记「由 OV-T-01 部分批准后升级」
            → 归口 CEO 终审
```

三种终局：**① 全额批准**（缺口挂营销预算科目，熔断线重算）→ **② 部分批准 + 升级**（余量继续上收）→ **③ 驳回**（缺口无出处，全额扣留存毛利）。

**决策理由**：真实企业审批从来不是一次性的。让系统自动升级，而不是让人自己判断「这事该不该往上报」，才叫闭环。

### 4. 设计决策三：熔断口径（踩坑后修正）

**熔断判定** = 超支率（缺口 ÷ 预留池）> 25% **且**缺口尚无已批准处置。熔断只卡**新增投放**（藏品新批次铸造转「待财务放行」），不停存量核销 —— 停投放伤体验，放量则亏更多。

> **踩坑记录**：初版把判定对象写成「未获审批覆盖的超支 ÷ 池 > 线」。因为初始数据里已有一条已批 ¥2,140，实际未覆盖只有 20.6% < 25%，**熔断死活不触发**。探针直接抓到了。**教训：熔断要看「成本本身是否失控」（超支率），而不是「还剩多少没批」—— 后者会因为部分审批而失真。**

### 5. 设计决策四：审批只换科目，不破恒等

超支调剂属于平台**内部科目间搬移**（营销预算 ↔ 留存毛利），不是新增支出。因此：

- **批与不批，游客实付 ¥298 的五口径分账合计都恒定**；
- 审批的价值不在于改变总额，而在于**有授权、有留痕、有责任人**；
- 不批的超支直接从利润里扣，年底自然暴露。

这条约束让「审批」与「账实一致」两个目标不打架 —— 是本轮能同时成立的前提。

### 6. 设计决策五：`m.amt` 是账实权威

协议变更生效时**当场重算** `m.amt = cnt × 新单价`，而不是让 `rightsLineNet()` 每次现算。

> **踩坑记录（重要）**：v1.8 初版把 `rightsLineNet` 改成 `m.cnt × agrPrice(m) − cut`，结果 **crosstrace 从 50/0 掉到 47/3** —— v1.7 的申诉受理是直接给 `m.amt` 加钱（+¥136），现算式子完全读不到 `m.amt`，导致成本不联动。**教训：同一笔钱绝不能在两处各算一遍。** 现在 `m.amt` 是账实权威（协议变更时重算、申诉受理时上浮），`net` 只负责扣差异核减，`agrPrice` 只管展示。

### 7. 跨端联动效果（实测）

商户端发起协议变更 → 运营端待审批队列可见 → 点「同意变更并生效」：

| 指标 | 变更前 | 变更后 |

## 第二十一章 · v1.9 下期预算预测 · 事前预警（成本控制从事后追认到事前管理）

**时间**：2026-10-21 09:55–10:40
**触发**：v1.8 交付时我建议优先做「超支预警前置」，原话是「审批做得再漂亮，事后才知道超支也只是补票，预警才能让成本控制从事后追认变成事前管理」。用户批复「按照你的建议做，做完之后在全回归检测看看是否有 BUG 或者产品体验上的不足」。

### 1. 为什么必须前移（业务判断）

v1.8 把超支的**事后处置**做闭环了：谁批、批多少、超额怎么办、熔断，全有。但闭环的位置在**结算之后**——本期账已经花超了 ¥7,594，才走审批补票。真实运营里，这时候钱已经付出去了，审批只是追认。

成本控制的价值区间在**事前**：账期还没开始，就能回答「按当前节奏，下期会超多少、池子哪天见底、现在动哪一刀最有效」。这就是本轮的全部动机。

### 2. 设计决策一：周节奏是历史事实，账实是当前账面——两者分开

这是本轮最核心的模型决策，也是踩坑踩出来的。

初版把趋势增速的分母写成 `全期日均 = 本期实付 ÷ 已过天数`。看起来天经地义，直到探针跑出一个诡异结果：**协议变更批准后，预测成本一分没降**（¥44,787 → ¥44,787）。

排查后发现是两个错误叠加：

1. **分母被账面污染**：协议变更一生效，`m.amt` 重算、`net` 从 ¥34,116 降到 ¥32,468，全期日均跟着从 ¥1,795.6 缩到 ¥1,708.8，趋势增速反而从 +31.3% 「涨」到 +37.9% —— **降本动作让趋势看起来更糟**，完全违背直觉；
2. **两次预测值阴差阳错相等**：¥34,116 × 1.313 ≈ ¥32,468 × 1.379 ≈ ¥44,787。如果不是探针对「变更后预测必须下降」下了硬断言，这个 bug 会带着一个看似合理的数字活下来。

修正后的模型：

```
周节奏（历史事实，恒定）  ：三周合计 = ¥34,116，近周日均 = ¥2,357.2
账实（当前账面，可变）    ：协议变更生效后 m.amt 重算，net 自动下降
预测 = 账实 × 节奏倍数    ：节奏倍数 = 1 + (近周日均 ÷ 全期日均 − 1) = 1.313
```

**教训：任何「趋势/比率」的分母，必须是不随本次动作漂移的事实基数。拿可变账面当基数，动作本身就会扭曲指标——这和 v1.7「核销率两套口径」是同一类错误的变种：指标被它不该受影响的变量污染。**

### 3. 设计决策二：全期均速是后视镜，近周节奏才是前挡风

为什么外推用「近周日均」而不是「全期日均」：

| 口径 | 数值 | 含义 |
|---|---|---|
| 全期日均 | ¥1,795.6 / 天 | 19 天平均——把前面慢的日子也摊进来了 |
| 近周日均 | ¥2,357.2 / 天 | 最近 5 天的真实节奏——金秋旺季客流正在上行 |
| 趋势增速 | +31.3% | 节奏还在往上走的证据 |

用全期均速外推 = 假设未来 19 天和前 14 天一样慢；用近周节奏外推 = 假设未来和最近一样快。**成本控制要按最坏的准备**，所以预警取近周口径。UI 上两个数字并排显示，标注「后视镜」与「前挡风」——把口径选择权和一目了然的依据都交给看的人。

不完整周（W43 只有 5 天）**按天折算**成日均再参与比较，否则短周会被低估、环比失真。这一点写进了断言。

### 4. 设计决策三：三态预警 + 见底日

- **分级**：预测超支率 ≤ 25%（熔断线）绿灯；25%–50% 黄灯；> 50% 红灯。当前 68.9% → 红灯，破线 2.8 倍。
- **见底日**：池 ¥26,522 ÷ 近周日均 ¥2,357.2 = **第 11.3 天**见底，早于账期结束 7.7 天。这是全卡最有冲击力的一个数字——它把「超支」从会计概念变成「还有 11 天」的倒计时。
- **建议预留单价**：¥14.9 → **¥25.92**（预测单均 ¥25.16 + 3% 缓冲）。这个数字很刺眼，但它是诚实的：按当前趋势，下期权益成本会吃掉单均 ¥25.9，预留 ¥14.9 从一开始就是错的。

### 5. 设计决策四：三个 what-if 同屏测算，且预览值 = 批准后实际值

预警光给数字不给动作，就是一份报告。三个动作全部带影响测算：

1. **协议调价（首选）**：AG-1019-02 生效后预测 ¥44,787 → **¥42,623**、超支率 68.9% → 60.7%；
2. **重设下期预留**：¥14.9 → ¥25.92，一次性覆盖预测成本；
3. **收缩投放 10%**：预测降至 ¥40,308、超支率 52.0%，**仍破线**——这条是故意放的对照：证明单靠压投放救不回来，必须动价格。

**关键约束：what-if 与真实模型必须同式。** 初版 what-if 用 `fcNext − 节省额`（¥43,139），而真实模型是 `(net − 节省额) × 1.313`（¥42,623），两个数不一致——用户照着预览做决策，批准后看到的却是另一个数。改为同式后，「预览值 = 批准后的实际值」成为硬断言（ovprobe + crosstrace 双守卫）。

### 6. 设计决策五：入口不止一处——否则红灯没人看见

第一版只把预警做在「权益核销与结算」子页里。回来看这就是**产品体验上的真不足**：运营打开 demo 落在驾驶舱，红灯埋在四级页面下，等于没有预警。

补救：**风控 tab 顶部挂同源预警卡**（红灯/结论/见底日/一键跳转）。风控是成本风险的天然归属，运营每天看的地方。预警卡与权益页同源派生（同一个 `fcState()`），不存在两套数。

- 仅当 `innerWidth ≥ 1200 且 innerHeight ≥ 700` 时自动进入演示模式 —— 工具视口 430 永不触发，**自动化零影响**（fitprobe 第 1 段就是守这条的硬断言）；
- 手动退出状态写 `localStorage('wf-demo-fit-off')`，退出后按钮仍显示可再开；按钮仅在「大窗口或曾退出」时出现，小窗/工具视口下不渲染，避免被遮挡检测误伤；
- `resize` + `ResizeObserver` 双触发重算（侧栏内容变化会改变舞台高度；transform 不影响布局，不会递归）。

**实测**（fitprobe 19 条）：1600×900 下 scale=0.9348、scrollHeight=900=innerHeight（整页零滚动）、按钮文案「退出演示模式」；430×920 下 transform 为空、按钮 display:none；退出/再开/小窗回退三态正确。

合计: 30 PASS / 0 FAIL
TypeError: Cannot read properties of null (reading 'find')

## 第二十三章 · v1.10 平台运营端经营口径引擎 + 驾驶舱重排

> 用户原话：「平台运营这个页面感觉没做好，你在思考和完善一下，包括一些演示数据的展示你都只是近 7 日，没办法切换到最近 30 日的」

### 1. 症状是一个下拉框，病根是三层结构缺陷

先按原话去找，确实一眼就能看到：`DB.admin.trend` 是定长 7 元素数组，`近 7 日 GMV`、`近 7 日 · 四端合计` 都是硬编码字符串，**没有任何切换机制，也没有「上一期」这个概念**。

但如果只加一个下拉框，会立刻撞上第二层：

6 张 KPI 卡里的涨跌幅全是字面量 —— `▲ 12.5%` / `▲ 8.2%` / `▲ 2.1%` / `▲ 3.4%` / `▲ 1.8%` / `LTV/CAC 5.7`。**切换口径时数值会跟着变、涨跌幅却一动不动**。演示时被问一句「30 日的环比怎么和 7 日一模一样」，当场就穿帮。这不是补丁能盖住的问题，它违反项目里那条铁律：视图层不得硬写数字。而要算环比，就必须先有「上期」，等于要把整条数据链重建。

第三层最伤专业度，也是用户那句「没做好」的真实来源：

同一个驾驶舱里并排放着两个模块讲同一件事，**数字还完全不同**：

| 模块 | 数据源 | 上海青浦 | 湖州安吉 | 苏州 | 上饶婺源 |
|---|---|---|---|---|---|
| 单城经营对比 | `DB.x.cityRank` | ¥48.6 万 | ¥31.2 万 | ¥26.9 万 | ¥12.5 万 |
| 城市经营排名 | `DB.admin.cities` | ¥42,180 | ¥19,320 | 吴江 ¥28,640 | ¥12,860 |

不仅量级对不上（48.6 万 vs 4.2 万），连城市列表都不一样（一个有苏州·姑苏，一个是苏州·吴江汾湖）。**这种自相矛盾在董事长级别的演示里是致命的** —— 对面只要横向扫一眼就能发现，一旦发现，前面讲的所有架构都不可信了。

再加上：4 个功能入口（eco-entry）横在 KPI 和业务图表之间，把驾驶舱做成了「功能目录」；全篇没有一条目标线，只有「多少」，没有「好不好」。

**结论：得先把数据层重建，再谈视图。**

### 2. 设计决策一：一份逐日底账聚合出所有口径，绝不手写三套数字

最省事的做法是手写 7 日、30 日、90 日三组数。**这条路是死的**：三组数必然互不自洽 —— 7 日之和不会等于 30 日里的那 7 天，30 日又不会等于 90 日的切片。探针只要断言一次「7 日 < 30 日 < 90 日」就会全线飘红，而且演示时鼠标来回切两下，数字对不上就露馅。

所以改成：**建一份 180 天的逐日底账，所有口径都由它聚合**。

```js
DB.x.ledger = (function(){
  const LAST = new Date(2026, 9, 19);            /* 演示数据截止日 */
  const N = 180, rnd = _lcg(20261019), out = [];
  for(let i = 0; i < N; i++){
    const back = N - 1 - i;
    const dt = new Date(LAST.getTime() - back * 86400000);
    const t = i / (N - 1);
    const ramp = 0.70 + 0.58 * t;                /* 月度爬坡 0.70 → 1.28 */
    const wd = dt.getDay();
    const wk = (wd === 6 || wd === 0) ? 1.22 : (wd === 5 ? 1.10 : (wd === 1 ? 0.96 : 1));
    const noise = 0.94 + rnd() * 0.12;
    const ord = Math.max(8, Math.round(37 * ramp * wk * noise));
    const aov = 258 + Math.round(rnd() * 8) * 10;  /* 258–338，中枢 298 */
    const vr  = 0.70 + rnd() * 0.06;
    const lag = back < LAG.days ? LAG.factor : 1;
    out.push({ d:..., m:..., g:..., wd:...,
      ord, gmv: ord * aov, aov,
      vf: Math.round(ord * vr * lag),
      ugc: ..., rep: ..., nat: ..., cac: ... });
  }
  return out;
})();
```

三个细节值得记下来：

- **确定性伪随机（固定种子的 LCG）**，不是 `Math.random()`。底账必须每次加载完全一致，否则每刷新一次页面数字就变，探针无法断言，演示也没法复述。
- **客单价中枢锁死在 ¥298**（258–338 均匀取整），因为整个项目「一单 ¥298 分账」的恒等式是这个原型的信誉支点。实测全期客单价 ¥301.5，落在容差内。原来 `monthGmv:119700 / monthOrders:3000` 算出客单价 ¥39.9，与 ¥298 差一个数量级 —— 这本身就是个埋了很久的雷，顺手拆掉了。
- **最近 4 天核销率按 0.92 折损**（`LAG`）。这不是为了好看，是为了让「短口径核销率偏低」成为可解释的事实，而不是看起来像 bug。

聚合层三个函数分工明确：

| 函数 | 职责 |
|---|---|
| `_window(k)` | 给出该口径的 [本期窗口, 上期等长窗口]，本月口径按自然月切并对上月同期 |
| `_agg(rows)` | 窗口内加总，比率型指标（复购/自然获客/CAC）按**订单数加权**，不是简单平均 |
| `_buckets(rows, 10)` | 趋势分列，自动换粒度（≤10 列），列内取**日均** |

`dashRange(k)` 一次产出全部：KPI 值 + 环比 + 趋势 + 漏斗 + 分城 + 收入结构 + 诊断结论。视图层只负责渲染，一个数字都不许自己算。

### 3. 设计决策二：分城环比不能「给固定值再归一化」

这是本轮最隐蔽的一个坑，值得详细记。

分城 GMV 有个硬约束：**各城合计必须等于大盘**，否则驾驶舱自己就打自己脸。初版的写法是给每城一个固定环比 `up`，反算上期权重再归一化到大盘：

```js
const rawPrev = cities.map(c => c.w / (1 + c.up/100));   // ← 错
const sumRaw  = sum(rawPrev);
const gp      = prev.gmv * rawPrev[i] / sumRaw;
```

7 日口径下看着没问题（大盘 +5.0%，苏州 −4.2%）。但切到 90 日，大盘环比是 **+33.7%**（底账爬坡的必然结果），归一化就把所有城市的上期值等比例压小，于是**苏州变成 −21%**。

```
90 日：大盘 +33.7% / 苏州 −21.0%   ← 差 55pp，荒谬
```

一个成熟市场一个季度不会掉 21%，而大盘同时在涨 33.7% —— 这两个数字放在一起，任何一个懂业务的人都会当场质疑。

**根因**：给的是「绝对环比」，但归一化会把它当地「相对大盘的偏离」来用，两者量级完全不同。

**改法**：把 `up` 改成 `dev`（相对大盘的偏离，pp），环比 = 大盘环比 + dev，再反算上期；长尾「其他城市」不参与计算，直接吸收上期差口。

```js
const rows = DB.x.cities.map(function(c){
  const g = cur.gmv * c.w;
  return { c: c, g: g, p: c.core ? g / (1 + (delta.gmv + c.dev) / 100) : null };
});
const pCore = _sumBy(rows, r => r.p || 0);
const iOther = rows.map(r => r.c.core).indexOf(false);
if(iOther >= 0){
  const rest = prev.gmv - pCore;
  rows[iOther].p = rest > 1000 ? rest : prev.gmv * rows[iOther].c.w / 100;  // 兜底防空
}
```

于是：苏州在 7 日是 **−4.0%**（短期真跌），在 90 日是 **+24.9%**（长期仍增长，只是跑输大盘）—— **短期波动与长期趋势不再互相污染，这恰恰是「多口径」存在的意义**。同时「分城上期合计 = 大盘上期」依然精确成立（探针实测差 <¥2）。

### 4. 设计决策三：趋势柱必须用「日均」，不能用「段合计」

本月 19 天，分 10 列，每列 2 天 —— **尾列只有 1 天**。

用「段合计」做柱子，尾列就只有相邻列的一半高：

```
28.5  32.9  27.7  26.8  30.8  31.6  28.5  32.7  32.8  [12.8]   ← 断崖
```

一眼就是假的：10 月 19 日怎么会当天掉 60%。这不是数据问题，是**轴不一致**问题 —— 拿 1 天的量去和 2 天的量比。

改成一律取**日均**后，每列含义完全一致：

```
14.3  16.4  13.8  13.4  15.4  15.8  14.2  16.3  16.4  [12.8]   ← 正常波动
```

附带一个巨大好处：目标线从「每列目标 = 日均 × 每列天数」变成**恒定的水平线**（¥15.0 千元/日），四个口径可以直接横向对照 —— 7 日的柱子贴着目标线上下跳、90 日的柱子整体压在目标线下方，一眼就能读出「短期达标、长期欠口」。这比任何文字解释都直观。

探针为此加了硬断言：`每列 v 严格等于 sum ÷ 天数 ÷ 1000`，且四个口径的 `tv` 必须完全相同。

### 5. 设计决策四：核销率先扣在途折损，剩下才是真问题

7 日核销率 69.8%，目标 72%，差 2.2pp。初版判断逻辑是拍了个天数阈值：

```js
} else if(r.days <= 7){    // ← 拍脑袋
  判「在途折损」
} else {
  判「实质下滑」
}
```

这个逻辑看着能用，实际会误判：本月口径 19 天，核销率 71.6%，差 0.4pp，因为 19 > 7 就被判成「核销率实质下滑，需核查商户履约」。—— 差 0.4pp 就要去查商户，这是让老板白跑一趟。

**改成定量扣除**。在途折损额度 = 折损率 × 在途天数 ÷ 区间天数：

```js
const drag = (1 - LAG.factor) * Math.min(LAG.days, r.days) / r.days * 100;
```

| 口径 | 核销率 | 缺口 | 可解释折损 | 判定 |
|---|---|---|---|---|
| 近 7 日 | 69.8% | −2.2pp | **4.57pp** | 在途未核销（正常） |
| 本月（19 天） | 71.6% | −0.4pp | **1.68pp** | 在途未核销（正常） |
| 近 30 日 | 72.3% | +0.3pp | 1.07pp | 健康 |
| 近 90 日 | 72.5% | +0.5pp | 0.36pp | 健康 |

**区间越短，虚低越明显** —— 这个规律本身就是最好的演示素材：同一门生意，换个口径看，结论从「要查商户」变成「完全正常」，而两者都对。这正是多口径驾驶舱的价值所在。

### 6. 设计决策五：删掉「今日」口径

一度加过「今日」口径（单日），想让实时性更强。实测后果：

- 单日样本下城市环比出现「苏州 **−35.0%**」、「大盘 **−26.0%**」—— 纯噪音，毫无业务含义
- 一根柱子铺满整个图表宽度，不像图，像色块
- 诊断结论开始胡说：单日 46 单，说「按当前日均需再提 17%」

**单日不是区间分析的极端情况，它是另一种东西**。真实 BI 里今日看板比的是「昨日同期」和「今日目标进度」，不做结构归因。

**决策：删掉。** 实时性由 hero 上的「实时」徽标 + 「实时业务流」模块承担，与区间分析彻底分开。口径最终定为四个：近 7 日 / 近 30 日 / 近 90 日 / 本月。

> 少一个口径不是缩水，是去掉一个会产出错误结论的入口。

### 8. 三个渲染 bug（都是量出来的，不是看出来的）

这三个坑的共同点：**目测看不出来，必须量 DOM**。

1. **目标虚线画到了容器顶端**
   写法 `position:absolute; inset:0; bottom:42%` —— `inset:0` 已经把 `top` 设为 0，随后 `bottom` 只改变高度，`border-top` 永远落在 div 的顶边，也就永远在容器最上方。截图看不出来（它确实是一条线，只是位置错了），是测量 `lineTop` 与预期值差 24px 才发现的。改成纯 `top` 定位，实测 `lineTop === expectTop` 精确相等。

2. **柱子被标签挤扁，实际高度与刻度不符**
   `.bcol` 是 `flex-direction:column`，里面塞了 `<b>`（数值）、`.bfill`（柱）、`<span>`（标签），总高超出容器 → `flex-shrink` 生效把 `.bfill` 压小。`maxV` 那根柱本该 71px，实测 64px，于是目标虚线（按 71px 算的）永远对不上柱子。改成「显式 74px 绘图区 + 标签独立成行」，柱子高度精确可控。

3. **柱高实测 0px**
   换成绝对定位后，包裹层只给了 `position:absolute;bottom:0;width:..%`，**没有高度**，里层 `height:100%` 没有解析基准 → 全部塌成 0。测量输出 `h:0` 才暴露。补 `height:100%` + `display:flex; flex-direction:column; justify-content:flex-end` 后正常。

**方法论沉淀**：涉及「百分比高度 / 绝对定位 / flex 收缩」的图表，**不要靠截图验收**，直接量 `getBoundingClientRect()` 并断言「实际值 === 计算值」。这三个 bug 全都能被截图"看起来还行"地放过。

## 第二十四章 · v1.11 演示数据厚度 + 全量互动体检 + 数字自洽收口

> 用户原话：「最好你还要在全量检查一下整个 demo，特别是功能的互动体验上，我过几天要去跟投资人演示，可以多造点数据。」

这句话里有三个要求，但真正的风险点藏在第三句的动机里：**要拿去见投资人**。这意味着评判标准变了 —— 不再是「功能有没有」，而是「对面盯着看十分钟，会不会当场问出一个我答不上来的数」。

所以这一轮没有从「加数据」开始，而是从「先测出哪里会露馅」开始。

### 1. 先做体检，再动数据：可点性 100% 不等于体验过关

第一步用的是现成的 `accept2.js`（逐 tab 全元素点击）。结果 10 PASS / 0 FAIL，看起来没问题。但它每行末尾有一串「失效」数字很扎眼：

```
运营端 [我的] 点击 7/18 · 失效11
商户端 [我的] 点击 5/14 · 失效9
商户端 [订单] 点击 10/20 · 失效10
```

查了实现才知道，这些「失效」是脚本自己的**快照漂移** —— 它先采集一遍 `onclick` 元素列表，然后逐个点击；每点一次页面重渲染，元素被替换，按「onclick + 文本」重新匹配就找不到了。也就是说：**它既没证明能点，也没证明不能点。**

于是重写了一套 `touchprobe.js`，分两层测：

| 层 | 做法 | 判据 |
|---|---|---|
| **可点性** | 不点击，只量 | 零尺寸 / `visibility:hidden` / `pointer-events:none` / `opacity:0` / 滚不到视口内 / `elementFromPoint` 命中别人（被遮挡） |
| **反馈性** | 逐个真点击 | 页面栈层数 / sheet 与 dialog 的 show / toast 出现 / `baseScroll.innerHTML` 长度变化 / 当前 tab / URL —— 任一变化即为「有反馈」 |

结果：**445 个可点元素，0 个不可点；346 次点击，0 个真哑点击。**

有 22 个被初版判为「无反馈」，逐个看全是同一类：**当前已选中的 tab**、**当前已选中的筛选条**。点它们本来就不该有任何变化 —— 是探针的误报，不是产品缺陷。这条经验写进了判据里：反馈性测试必须先排除「点击已激活态」。

> **v1.12 补记（口径修正）**：v1.11 当时是「先测出 22 个、再由人逐个判为误报」—— 结论对，但**报表上永远挂着 22 个红字**。v1.12 把判据写进探针本身：`SCAN` 采集时带 `on: e.classList.contains('on')`，`targets` 直接过滤激活态，并单独打印「已激活态跳过 N 个（点它无反应才是对的）」。现在 18 个 tab 实测 **422 个可点元素、0 不可点、315 次有效点击 0 哑点、跳过激活态 23 个**。
>
> 为什么值得改：一个长期输出「22 个哑点击」的探针，等于把真哑点藏进噪声里。**误报必须消灭在工具里，不能靠人事后解释** —— 换人接手、或隔三个月，没人知道那 22 个是良性的。

### 3. 三条真 bug（全是互动体检才暴露的）

**bug 1：审核连点三次，删掉三条不同记录。**

```js
onclick="handleAudit(${i},'pass')"     // 按索引传参
function handleAudit(i, act){ const x = DB.admin.audits[i]; ... }
```

连点三次的时序是：三次 click 在同一个 tick 里同步触发，`renderBase()` 还没跑，DOM 也没更新，所以三次拿到的都是 `i=0`。第一次删掉第 0 条，第二次第 0 条变成了原来的第 1 条 —— **于是删了三条**。

这不是「多点了一下」这种小事。演示时手一抖（或者对面帮你点两下）就少了三条待审，而屏幕上只会显示「已通过」，看不出发生了什么。

改法：给每条审核项赋稳定 id（`AU0`/`WN0`），按 id 定位。

```js
function handleAudit(id, act){
  const i = DB.admin.audits.findIndex(function(a){ return a.id === id; });
  if(i < 0) return;          // 第二次点就找不到了，天然幂等
  ...
}
```

风控预警的 `handleWarn` 是同一个毛病，一并改掉。

**bug 2：开场要四步才能进演示。**

`S.loginStep` 默认 `'phone'` —— 打开是手机号登录，要输手机号 → 拿验证码 → 输 6 位 → 才到身份选择。对一个要现场演示的原型，这四步纯属摩擦，而且验证码是假的，对面一看就知道在走流程。

改成默认 `'role'`：打开就是 4 张身份卡，一键进入。「使用手机号登录」保留为底部二级入口（产品能力还在，只是不挡路）。

**bug 3：身份选择页左上角多一个返回箭头。**

```js
${S.loginStep!=='phone' ? '<button class="login-back" ...>' : ''}
```

`!=='phone'` 把 `role` 也算进去了，于是最外层页面出现了返回箭头，点下去还会跳到验证码页。改成 `==='code'`。

### 4. 五组数字互相矛盾 —— 这一节才是这轮的重点

数据一多，藏在其中的矛盾才显形。**这些矛盾的共同点是：单看每一个数字都合理，放在一起就荒谬。** 而投资人恰恰最爱横向扫。

**（1）一个店干翻整个大盘**

| | 数值 |
|---|---|
| 商户「今日流水」 | **¥16,842 / 42 单** |
| 平台「今日 GMV」 | **¥12,788 / 46 单** |

单店做了大盘的 **132%**，单量占 91%。这是最容易被一眼看穿的那种错——任何做过生意的人都会立刻问「你这家店是全平台的 1.3 倍？」

改：头部商户约占大盘三成 → `today 14 单 / ¥4,586`，`monthOrders 412`。同时把商户编号从 `M20261018`（看起来像 2026-10-18 入驻，即开业第 1 天）改成 `M20250312` —— 开业一天却有 7 日流水，本身也是矛盾。

**（2）7 日分润比一个月赚得还多**

`partnerTrend` 合计 **¥8,280**，而 `monthEarn` 只有 **¥3,864**。一周挣的是一月的 2.1 倍。

同时 16 个下线的返佣明细合计是 **¥13,884**（每笔严格按 8% 费率算出来的），又是第三个数。

三个数取真相：**以明细为准** —— `monthEarn = 13,884`，7 日分润按 19 天折算为 `13,884 × 7/19 = 5,115`。

**（3）团队榜与成员列表是两套完全不同的名单**

| 模块 | 名单 |
|---|---|
| 团队本月榜 | 张敏·黄金 / 李伟·白银 / 王芳·白银 / 陈磊·青铜 |
| 团队成员 | 瑜伽馆·李店长 / 咖啡店·小王 / 兼职导游·陈姐 / 大学生·小林 … |

不仅人不同，头部还写着「12 人」而列表有 16 条。这跟 v1.10 在驾驶舱里修过的「单城经营对比 vs 城市经营排名」是同一类病 —— **两个模块讲同一件事，数据来自两处**。

改：团队榜从 `referrals` 按有效订单排序派生取前 4，`downline` 派生为 `referrals.length`。

**（4）累计收益、月度账单、提现记录三者对不上**

原来：`totalEarn 8,640`，10 个月账单合计约 8,500，提现记录合计 7,020 —— 三个数互相不挨着。

重算成一个**能当场对账的闭环**：

```
累计收益 98,340
− 已提现 78,600（8 笔成功，另有 1 笔失败样本）
= 可提现 19,740
```

并且 10 个月账单合计**恰好等于** 98,340。这一组数字现在是演示素材而不是风险：可以主动说「这个合伙人累计赚了 9.8 万，提走 7.86 万，账上还有 1.97 万」——对面拿计算器也算不出错。

**（5）图表末日 != KPI 今日值**

商户「近 7 日流水」图最后一天 **21 千元**，而 KPI「今日流水」写 **¥16,842**。同一个页面，两个「今天」。

改：初始化时把 `merchTrend` 末日回写为 `merch.gmv / 1000`。顺带修了日序 —— 原标签是 `一二三四五六日`，但演示基准日 10-19 是**周一**，末日标签错了一天。改成 `二三四五六日一`。

还有 `merch.pending`（待核销数）是手写字段，和 `orders` 里的实际待核销条数各算各的。改成初始化派生：

```js
DB.merch.pending = DB.merch.orders.filter(o => o.status === '待核销').length;
```

这样以后再加订单，这个数不会再脱节。

### 5. 顺手打通一条断掉的联动

商户核销后，原来只改了 `DB.merch.pending` 和 `DB.admin.verifyRate = min(99, +0.2)` —— 但驾驶舱的核销率早已改成从 `DB.x.ledger` 派生（v1.10），所以**商户端核销了，驾驶舱纹丝不动**。而 `ame` 页显示的又是「今日核销率 63.1%」，跟驾驶舱 30 日的 72.3% 是两个数，**同一页面上写着两个不同的核销率**。

改两处：
- `applyVerify` 真实回写底账当日核销数 `L.vf += 1` —— 核销一单，驾驶舱近 7 日核销率真的会动（69.80% → 70.09%，实测）
- `ame` 的核销率改用 `dashRange('30d').cur.verify` 同源派生，并标注「30日」，与驾驶舱口径一致

| 工具 | 断言的「不能违反」 |

| `consisprobe.js`（39 条） | 列表厚度下限 / 同源数字不变脸 / 跨端核销码打通 / 写操作真联动 / 文案与数据一致 |

### 8. 全量回归的红灯：三套探针债（非产品缺陷）

18 套跑完，3 套红：`missiontrace`（22/1）、`playtrace`（EXIT 1）、`accept2`（EXIT 1）。逐个拆开看，**没有一个是产品坏了**，全是「测试脚本与产品改动脱节」：

| 红灯 | 根因 | 性质 |
|---|---|---|
| `missiontrace` 「渲染 3 张任务卡」 | 断言写死 `=== 3`，本轮数据扩到 12 条 | 数据扩容 → 断言失效 |
| `playtrace` 找 `#btnGetCode` 找不到 | 本轮把登录默认入口改成身份卡，手机号登录降为二级入口 | 入口变更 → 选择器失效 |
| `accept2` 同上，第一步就中止 | 同上 | 同上 |

**为什么必须当天修掉，而不是"知道是误报就行"**：回归是唯一能兜住演示事故的网。网上一旦长期挂三个红灯，下次真出 bug 时，它跟"已知误报"长得一模一样——那时没人会去查。**假红灯的代价不是浪费时间，是让真红灯失去意义。**

修法（都是加固，不是放水）：
- `missiontrace` 改成「渲染条数 = `DB.missions.length` 且 ≥3」——从"写死数量"改为"跟数据源对账"，以后再扩容自动适配。
- `playtrace` / `accept2` 各加一步「若当前不是手机号步骤，先点‘使用手机号登录’」，然后照原流程走。**手机号链路仍被完整覆盖**，只是多了一步显式切换，而不是把这段测试删掉。

一条通用教训，已写进 README 与 MEMORY：

> **改入口等于改契约。** 凡动登录页、首页默认落点、主导航结构，必须同步扫 `tools/` 里所有硬编码的选择器与"数量/文案"断言。产品改动只改 `src/`、测试不动，是假绿。

修完单跑复验：`missiontrace` 23/0、`playtrace` 4 场景 0 FAIL（29 PASS）、`accept2` 10 PASS / 0 FAIL，再跑一次 18 套全量确认无回退。

另注：`accept2` 在本轮数据量下耗时从 12s 涨到 **12 分钟**（它按快照逐个点击全部元素，元素数随数据条数线性增长，且「失效 N」本身就是快照漂移的假信号，已被 `touchprobe` 的双层测取代）。目前仍留在 `full` 组里做兜底，但如果以后全量回归时长成为负担，**第一个该移出的是它，不是 `touchprobe`**。

## 第二十五章 · v1.12 把四个身份说清楚：同一个入口，四套内容

### 1. 症状描述是「入口重复」，病根是「定位错误」

用户的原话是：

> 「你能不能将 4 个身份说清楚，为什么每个身份都是展示同样的决策说明和入口？」

截图里那一行是「生态架构与方案 / 三层架构 · 六大引擎 · 五阶段验收」。它出现在游客、合伙人、商户三个端的「我的 → 通用」里，一字不差；平台运营端在「方案与数据」里也有一条同样的。

第一反应容易判成「入口重复了，删掉三处就行」。但真正的问题不是重复，是**这条内容根本不属于这三个角色**：

- 它是**给投资人/评审看的方案文档**（三层架构、六大引擎、五阶段验收），讲的是「这家公司怎么做这套系统」；
- 而「我的」页是**给角色用的功能入口**，讲的是「我这个身份能干什么」。

把内部 PRD 挂进用户 App，四端还完全一样 —— 这等于在演示时主动告诉对面：**这四个身份只是换了个图标和颜色**。对一场要靠「四端闭环」立住的投资人演示来说，这是硬伤，比任何一个数字错误都更伤。

### 2. 决策：不是删入口，而是补上「角色说明书」

三个候选方案：

| 方案 | 做法 | 判断 |
|---|---|---|
| A | 三端直接删掉这一行 | 删除能止血，但也删掉了唯一一处「讲清角色」的位置，四个身份依旧说不清 |
| B | 四端各起一个不同名字的入口 | 名字不同、内容一样，是更精致的糊弄 |
| C | **同一入口，四套内容**（采用） | 「我的角色 · 生态位」本身就是一个对照系：同一个问题，四个身份四个答案 |

选 C 的理由：用户问的是「把四个身份说清楚」，而**说清楚**最有效的方式不是四段文案，是**同构对比**——同一条链路、同一组问题（我在第几环 / 能做什么 / 钱怎么算 / 不做什么），四端各答一遍。

### 3. 五环价值流：用「一单 ¥298」的流向定义身份

身份差异如果只写职责，会写成四段形容词。改成一条**价值流**就有了坐标：

```
① 分发获客 → ② 体验消费 → ③ 内容沉淀 → ④ 履约核销 → ⑤ 治理结算
```

- 游客 = ②③（消费创造收入，体验产出内容）
- 合伙人 = ①③（带来的人产生消费，内容做转化）
- 商户 = ④（把线路兑现成真实体验，核销即进入结算）
- 平台运营 = ⑤（不参与交易，定义交易如何发生、如何被结算与约束）

这一条链不是编的，它就是分账恒等式的空间投影：**同一笔 ¥298，游客付钱 → 商户履约 → 合伙人分佣 → 平台留毛利**。所以页面下方直接写这句话，把「你在第几环」和「钱怎么流」钉在一起。

### 4. 「你不做什么」比「你能做什么」更能说明身份

四个身份最容易混淆的不是功能，是**边界**。所以每端都加了三条硬边界：

- 合伙人：不按层级计酬（下线拉下线不产生任何返佣）／不碰资金池／不代收货款
- 商户：不参与平台定价与分佣规则／看不到游客真实手机号／核销即进入结算，撤销须走退款冲正
- 平台运营：不直接经手用户资金／不修改已上链存证／不替商户做经营决策
- 游客：不参与分账与结算／旅豆不可提现／看不到其他用户信息

这几条同时是**合规话术**。演示时被问到「合伙人会不会变成传销」，答案就在这一页上，不需要临场组织语言。

### 5. 「其他三个身份看到什么」做成可点

底部列出另三端的层定位与职责，点一下直接切过去看同一个页面变成什么样（`rolePeek()`）。

这是**用户主动点击**，不违反「严禁身份自动切换」的红线 —— 红线针对的是系统在无操作时跳端。这里是演示中最有说服力的一个动作：同一条入口，四个颜色的页面，四套数字。

### 6. 视觉：四端各一个主色，并排不会认错

`eco-hero` 原本是固定深蓝底。v1.12 改为叠角色主色的径向渐变：

| 身份 | 主色 |
|---|---|
| 游客 | `#e87722` 橙 |
| 合伙人 | `#2f6f9f` 蓝 |
| 商户 | `#7b5aa6` 紫 |
| 平台运营 | `#0f766e` 青 |

四张截图并排放在一页 PPT 上，不需要看文字就知道是四个不同的视角。

### 7. 登录页同步说清楚

原来的四张身份卡只有「名称 + 一行职责」，四张卡视觉结构完全一致，第一眼无法对比。v1.12 每张卡补两行，全部从 `ENDS` 派生、不另存一份：

- 层标签：`ENDS[k].sub.split(' · ')[0]` → A 层 / B 层 / 履约层 / 管理舱
- 模块清单：`ENDS[k].tabs.length` + `tabs.map(t=>t.l)` → 「5 个模块　首页 · 主题游 · 商城 · 旅豆 · 我的」

副标题从「四个端共用同一 Travel ID，底层数据实时互通」改成「**四个身份 = 四套数据、四套功能、四套权限**，共用同一个 Travel ID，进入后可随时切换」。

改这一句是因为原话容易被理解成「四个端看到的是同一份数据」——恰好是这次被质疑的根源。

### 8. 数字一律派生，不新存一份

`rolePos()` 里所有数字都从 `DB` / `dashRange()` 现取，没有一处手写：

| 位置 | 取值 |
|---|---|
| 游客消费支出 | `DB.visitorOrders` 的 `price` 求和（¥9,958 · 16 笔） |
| 合伙人 | `totalEarn` 98,340 / `monthEarn` 13,884 / `withdrawable` 19,740 / `rate` 8% |
| 商户 | `today` 14 / `gmv` 4,586 / `monthOrders` 412 / `rating` 4.9 |
| 运营 | `todayGmv` 12,788 / `dashRange('30d')` 的核销率 72.3% 与 GMV 437,668 |

第一次写完自检时抓到一处：运营端「钱怎么算」里「今日 GMV · 46 单」与「今日订单 · 46 单」重复了同一个数，且第二行信息量为零 —— 改为「近 30 日 GMV ¥437,668 · 1456 单」。**同一张卡片里出现两个同样的数字，对面会怀疑你在凑行数。**

### 9. 验收

- `consisprobe` 39/0（数字自洽、跨端核销码、写操作真联动均未受影响）
- `uxprobe` 12/0，首屏 161ms
- 全量 18 套复验通过
- 新增截图目录 `shots_role/`：登录页 + 四端角色页各 3 张（顶/中/底），共 13 张

### 10. 一条可复用的判据

> **同一入口出现在多个身份下时，内容必须不同；内容若必须相同，说明它不属于这些身份。**

按这条判据回扫，还有两处同类隐患（未动，登记在案）：

1. 「切换身份」在四端都有 —— 合理，它是身份系统的通用操作，内容天然相同；
2. 「设置」只在游客端有，其余三端缺失 —— 反过来暴露了不一致，属于可补但不必在演示前补。

### 11. 修正：把手机号登录从「小字」提回「平级入口」

用户的第二句反馈：

> 「登录卡片包括验证那个挺好的，你为什么要隐藏？」

这条反馈打的是 v1.11 的一个过度修正。当时为了满足「从双击文件到看见核心画面不超过 2 次交互」，把默认入口改成身份卡直达，顺带把手机号登录压成登录页底部一行 11.5px 的小字：「或 使用手机号登录」。

问题在于：**缩短演示路径 ≠ 藏掉真实能力**。

验证码那 6 个格子、60 秒倒计时、脱敏后的 +86 13800006666 —— 这些本身就是「这是个真产品，不是画的原型」的证据。投资人想验证的时候，你不该让他在一行灰色小字里找。而且那行小字在 430px 宽度里几乎和「登录即代表同意《用户协议》」混在一起，视觉上是法务文案区，不是入口。

改成登录体顶部**分段器**：

```
[ 一键体验身份 ] [ 手机号 + 验证码 ]
```

- 默认停在左格（保住两步入场：双击 → 点身份卡 → 核心画面）
- 右格是**同级入口**，一点就到手机号表单，再一点就是验证码页
- 验证码页保留左上返回箭头回手机号页，分段器任何时刻可以切回一键体验
- 状态机：`role ⇄ phone → code`，全部路径都验证过

`setLoginMode(m)` 里有个细节：切到 `phone` 时，如果当前已经在 `phone` 或 `code`，直接 return，不重渲染。否则用户在验证码页点一下「手机号 + 验证码」，倒计时会被重置成 60s，看着像卡了。

### 12. 这条反馈修正的是什么认知

v1.11 的铁律 14 写的是「演示型原型的默认入口必须是最短路径」。这句话本身没错，但它容易被执行成「把长路径藏起来」。补一句才算完整：

> **默认走最短路径，但真实链路必须是同级可见的入口，不能降级成小字。**
> 判据：如果这个功能被问到「你们真的能做吗」，你能不能在 2 次点击内给出证据。答不上来，就是把证据藏了。

## 第二十六章 · v1.13 「左上角没有返回键」：查了两小时，结论是没有，但确实看不见

### 1. 症状与第一反应

用户的原话：

> 「里面很多页面左上角没有返回键你没发现吗？」

第一反应是「不可能，`push()` 里写死了 navbar + 返回键」。但顺着查下去，发现这句话里其实藏了**两个不同的问题**：

1. **返回键是否真的缺失** —— 可验证，可量化；
2. **返回键是否看得见** —— 也可验证，但过去从来没验过。

### 2. 把「有没有」量到底

写了三个探针，逐层排除：

| 探针 | 查什么 | 结果 |
|---|---|---|
| `_backdump` | 每页所有 `onclick` 含 `pop(` 的元素，打印类名与坐标 | 37 个二级页全部有 `.nav-btn`，位置在左上（相对屏幕 x≈8-14、y≈48） |
| `_backhit` | **命中测试**：取返回键中心点做 `elementFromPoint`，看落点是不是它自己 | 37/37 命中，无遮挡 |
| `backprobe`（保留为正式工具） | 4 端 × 37 页 = **152 次**，位置 / 尺寸 / 遮挡 / 图标粗细 / 底色 / 热区 | 全通过 |

结论很硬：**结构上不存在「没有返回键的页面」**。

顺带排除了两个假说：① `push()` 是唯一的建页路径（全仓只有一处 `S.stack.push`、一处 `pageStack.appendChild`），没有任何页面绕开它；② `.navbar` 没有任何 `display:none` 或按端隐藏的规则。

### 3. 但「看不见」是真的

把 37 页的顶部 200px 拼成对照表逐张看，才看清问题在哪：

- 箭头是 `i-back` 一条 path，`.ic` 全局 `stroke-width:1.8`、18px、`color:var(--ink)`；
- 演示模式 `transform:scale(0.93)`，投到 1024×768 投影仪上约等于 **1.2px 的细灰线**；
- 白 navbar × 细灰线 × 缩放 × 投影亮度 —— 结果是「那一片白，好像什么都没有」。

**这不是「没做」，是「做了等于没做」。** 于是按「一眼是个按钮」重做：

```
.nav-btn{ width:40px; height:40px; background:#eef1f5; border-radius:50%; color:#111418; }
.nav-btn .ic{ width:20px; height:20px; stroke-width:2.9; }
```

圆底 + 2.9px 加粗 + 近黑 —— 即使缩到 0.7 倍，也是一个有形的圆钮，不再是一条随时会消失的线。

### 4. 真正缺的那一类：跨 tab 跳转没有回头路

顺着「很多页面」继续找，找到唯一一处**真的没有返回入口**的场景：

在「我的」里点「经营驾驶舱 / 风控 / 准入审核 / 单城测算 / 订单与核销 / 货源中心 / 团队管理 / 商城好物」——这些行是 `setTab(...)`，**直接把底部 tab 换掉**。

用户的心理模型是「我点进了一个东西」，但落点是另一个 tab 首页：没有返回键、没有面包屑，只能自己去点底部 tab 或「我的」重新找。**从用户视角看，这就是「进去了出不来」。** 商户端和运营端尤其明显，因为「我的」是这一屏唯一的入口式列表。

### 5. 解法：一条 36px 的返回栏，只在「跳」过来的时候出现

```js
function jumpTab(k){                 // 「我的」里的入口行改用它
  const from = S.tab[S.end];
  setTab(k);
  if(from === k) return;
  S.ret = { tab: from, label: ENDS[S.end].tabs.find(t=>t.k===from).l };
  renderRet();
}
```

四条边界规则，全部写成了断言：

| 场景 | 行为 | 为什么 |
|---|---|---|
| 跳转进来 | 顶部出现「‹ 返回 我的」，内容下移 36px | 不压住页面标题 |
| 点底部 tab 栏 | 立即消失 | 用户已经自己导航了，再挂着就是噪音 |
| 进入二级页 | 收起；退回后恢复 | 否则会压在二级页自己的返回键上 |
| 切换身份 | 消失 | 「返回上一个 tab」跨端没有语义 |

踩到的三个坑（都记在这里，免得下次再踩）：

1. **`#baseScroll` 的 `padding-top:44px` 是状态栏让位，不是累计值**。一开始写成 48px，于是内容只下移了 4px，标题照样被返回栏压住 → 必须 `44 + 36 = 80px`。
2. **运营端首页是「沉浸头」**：`autoSB()` 会给首屏深色头加 `margin-top:-44px` 把头部顶到状态栏后面。返回栏一出现，这个负边距就让它钻进返回栏底下 → `renderRet()` 里要先清掉 `window.__sbBleedEl`。
3. **状态栏会反过来打脸**：内容被顶下去 36px 后，页面顶部变成白底，而状态栏还在按「首屏是深色头」显示白字 —— 白压白，时间和电量直接消失。修法是 `has-ret` 状态下强制 `applySB('light')`，并在 `autoSB()` 开头加同样判断，防止滚动时被改回去。

同一个病在别处也犯了一次：`playStart()` 里 `push(..., { sb:'dark' })`，但剧本沉浸页的顶部是**白色 navbar（带返回键）**，白字压白底 —— 时间和电量同样看不见。一并改成 `sb:'light'`。

### 3.3 踩到的坑：`renderBase()` 会把子页盖住

修法是新增 `rerenderTop()`：

```js
function rerenderTop(){

  if(top && typeof top.el.__rerender === 'function'){ top.el.__rerender(); return; }
  renderBase();
}
```

子页注册自己的 `__rerender`（商城与推广中心都注册了）。**判据：凡是"页内切换"的回调，在从 tab 首屏搬成二级页时必须一并改成 `rerenderTop()`。**

# 第二十八章 商城回 tabBar 一级位（v1.14.1 · 赵老师拍板回退）

## 1. 起因

v1.14 交付后赵老师质疑：**「商城为什么商城降为二级页？一级页挺好的啊」**。

核实定稿 §9 原文后确认：**这是我的过度执行**。定稿写的是「tabBar 4 个：首页 / 主题游 / 旅豆 / 我的（商城 P2 做小 SKU 后**再定** tab 位）」——「再定」是**延后决策**，P2 小 SKU 上来后商城本来就要回 tab 位。我把「延后」固化成了「降级」，还在 README / 交接记录里写成「定稿 §9：商城改为二级页」，把定稿口径写窄了。

## 2. 赵老师拍板（AskUserQuestion）

「改回一级 tab（推荐）」，同时知悉 trade-off：tabBar 5 个与定稿主句「tabBar 4 个」**字面冲突**，但符合定稿「P2 后再定 tab 位」的演进方向；微信 tabBar 5 个合规、无技术障碍；v1.12 及以前就是 5 tab，视觉交互已验证过几十轮。

## 3. 怎么改的

| 位置 | 改动 |
|---|---|
| `src/p4.html` | `ENDS.tourist.tabs` 4 → 5（首页/主题游/**商城**/旅豆/我的，shop 插在 theme 与 wallet 之间）；注释改为「v1.14.1 赵老师拍板商城回一级位」+ 完整理由 |
| `src/p6.html` | 删 `pushShopPage()`；商城分类 chip 由 `rerenderTop()` 改回 `renderBase()`（tab 首屏无子页盖叠）；旅豆页「商城好物」入口由 `pushShopPage()` 改回 `jumpTab('shop')`（带「返回 旅豆」返回栏，v1.12 同款 UX） |
| `src/p5.html` | 无需改动（架构面板不涉及 tab 数量，`resetDemo` 的 `S.tab` 初始为 home） |

## 4. 探针同步（6 个文件）

| 探针 | 改动 |
|---|---|
| `accept2.js` | 游客端 `tabs: 4` → `5`（循环按索引点全部 5 个 tab，商城在索引 2） |
| `deadlink.js` | 商城从二级页条目（`{name:'shop', enter:pushShopPage()}`）移回 tab 遍历（`{tab:'shop'}`） |
| `backprobe.js` | 跨 tab 用例由「旅豆→主题游」改回「旅豆→商城」（v1.14 曾因商城不是 tab 而换用例） |
| `touchprobe.js` / `heightscan.js` / `overlayprobe.js` | tab 表加回 `shop` |

| `v114smoke.js` | A 段断言改「tabBar 5 个、商城在一级位」；F 段整体改写为「商城回 tabBar 一级位」并新增 tabBar 商城位断言 → 28 条升 **29 条** |

## 5. 踩的坑

**探针里 CSS 属性选择器的引号嵌套**。`[onclick*="jumpTab('shop')"]` 写在 JS 模板字符串里，`\'` 转义后字符串字面量被单引号截断，表达式直接语法错误。改成免嵌套的 `getAttribute('onclick')==="jumpTab('shop')"` 循环匹配。教训：**探针里匹配带引号的 onclick，用 getAttribute 比较，别用属性选择器 substring 匹配。**

## 6. 结果

- 冒烟 **29 PASS / 0 FAIL**（v114smoke）
- 已复跑：`deadlink` 0 死链、`backprobe` 29/0（旅豆→商城返回栏 3 断言全过）、`touchprobe` 254 次点击 0 哑点、`missiontrace` 23/0、`accept2` 9 PASS / 0 FAIL / 0 WARN（游客端 Tab 数量=5 通过）
- 视觉：45 张全量截图，商城 tab 首屏（hero / 5 chip / 秒杀 / 严选列表）与 5-tab 高亮态无重叠无截断
- 产物 674,964 字符 / 约 757 KB

## 7. 沉淀

**「再定 / 后续再议」≠「现在定为 X」。** 执行文档时，括号里的延后措辞（「P2 后再定 tab 位」）不能固化为决定（「定为二级页」）。遇到这类措辞，要么保持现状、要么按终局演示，并向用户点明这个口径分歧——**不要替文档做它明确推迟了的决定**。已写入项目 MEMORY.md 铁律 24。

# 第二十九章 补商城 tab 图标 + 构建期图标引用校验（v1.14.2 · 赵老师截图发现）

## 1. 起因

赵老师截图反馈：**「你这个做了什么？商城的图片 logo 呢？」**——tabBar 上商城 tab 只有文字、图标空白。

## 2. 根因

`src/p4.html` 商城 tab 定义 `i:'i-shop'`，但 `src/p3.html` 图标库里**没有 `i-shop` 这个 symbol**。`ic()` 只是拼 `<svg><use href="#i-shop"></use></svg>`，use 指向不存在的 symbol，浏览器渲染空白。**v1.14 我加商城 tab 时引入**（改了 tab 定义，没核对面图标库）。

全量扫描后又发现同源问题：创作中心「提交作品」弹窗 4 处引用 `i-link`（复制链接 / 图文链接 / 素材链接 / 作品链接），同样不在图标库——历史遗留空白。

**为什么 20 套回归全是绿灯却没人发现**：冒烟测的是「tab 存在、可点击、页面渲染」，accept2 测的是「点击无遮挡、无 JS 错误」——没有一套断言「图标真的画出来了」。语法校验（node --check）只查 JS，不查资源引用。

## 3. 修复

| 项 | 内容 |
|---|---|
| `src/p3.html` | 补 `i-shop`（购物篮：篮体 + V 形提手 + 双竖线，与 i-bag 购物袋视觉区分，tabBar 23px 小尺寸可读）、`i-link`（双弧链条），symbol 79 → 81 |
| `build.py` | 新增**图标引用完整性校验**：扫全部 src 的 `'i-xxx'` 引用 vs p3.html symbol 定义，缺一个即构建失败；symbol 无引用给提示。本次即靠它抓出漏网的 `i-link` |

## 4. 验证

临时脚本 `tools/_iconcheck.js`（下划线开头，不随源码包分发）：

- **A 段**：8 个场景（登录层 / 游客端首页·商城tab·旅豆页 / 推广中心 / 创作中心 / 商户端 / 运营端）逐场景全页扫描 `svg use`——symbol 缺失或零尺寸即 FAIL，**8/8 PASS**
- **B 段**：tabBar 5 个 tab 图标逐一量尺寸，**商城 23x23（修复项）**
- **C 段**：提交作品弹窗 i-link **15x15（顺带修复项）**
- 复跑 `v114smoke` 29/0、`accept2` 9/0/0，tabBar 实拍 5 图标齐全

## 5. 沉淀

**「引用不存在的资源」是语法校验和点击回归的盲区**（铁律 26）。资源引用（图标 / 图片 / 锚点）必须在构建期做完整性校验——成本一行正则，收益是杜绝整类"看起来正常、其实空白"的缺陷。已写入项目 MEMORY.md。
